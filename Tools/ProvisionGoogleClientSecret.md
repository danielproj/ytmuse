# Operator-only Google configuration helper

This standalone Swift helper is not part of the app runtime. Root owns actual provisioning. Compile with `swiftc Tools/ProvisionGoogleClientSecret.swift -o <private-helper-path>` and review before execution. Invocation order is `--client-id <public-client-id> --app-executable <absolute-YTMuse-executable-path> --secret-file <owner-only-private-file>`. Never put a secret in argv or environment. The input file contains exactly one dotenv assignment named `YTMUSE_GOOGLE_DESKTOP_CLIENT_SECRET` (optional blank/comment lines and single/double quoted value supported; no evaluation or expansion); it must be a regular, single-link, current-owner 0600 file opened with O_NOFOLLOW. Do not cat its contents. The helper emits fixed messages only.

The target must be the exact signed YTMuse executable under MacOS. Public Security APIs validate its static signature, create SecTrustedApplication for that path, and supply an explicit one-target trusted list to SecAccessCreate. No interpreter/helper/all-apps trust is added. It opens the current user's standard login Keychain and updates/adds only generic-password service `local.native-music.development.sessions.oauth-config`, account equal to the supplied public Desktop client ID. It does not enumerate, delete, unlock, change defaults/security settings or invoke authentication UI. Existing ACL refusal fails closed with a fixed message; there is no fallback to broaden access. A rebuilt/re-signed app may need reprovisioning. Input-file lifecycle remains the custodian's responsibility.

The worker compiled this helper and tested only `--validate-private-input <dummy-file>` (no Security/Keychain API on that branch). **Keychain/ACL integration is not worker-verified**; no actual login or isolated Keychain provisioning ran. Root must review the one-app ACL choice and verify that the intended signed app can read through its existing interaction-disallowed provider. The SDK's SecAccessCreate documentation defines a supplied trusted list as the apps allowed without confirmation; unlike nil it does not default to the creating interpreter. Deprecated legacy standard-Keychain APIs are used deliberately to match the existing provider; no data-protection-Keychain guarantee is claimed.
