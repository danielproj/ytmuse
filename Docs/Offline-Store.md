# Retained media storage — W14 local rework

This implementation is in rework, not release acceptance. Stage A implements F1's authoritative anti-replay boundary. Stages A/B/C implement local protected authority, decoder/user-seek separation, typed native failures, bounded read/key state, source-time recovery and cooperative import. See the final W14 evidence for validated scope; no live-service or release gate is closed. W15 owns scheduling/UI and W36 owns actual source grants, encryption, renewal and source-time integration. All G01–G09 remain open. Owned fixture permissions are explicit test grants, never presumed official-app or Premium benefits.

## Protected authority and keys

`EncryptedStore` implements Domain's OfflineMediaStore and W04's account lifecycle participant. It requires `ScopedProtectedRecords`, a neutral capability beside SessionVault. The production implementation is native KeychainVault; there is no file-backed production authority fallback. The protected-record service scope uses the existing canonical account UUID, length-framed channel identity and region. The object name is `offline.object.v2.` plus SHA-256 of the canonical caller-supplied variant ID. Neither a latest-reference pointer nor a key-reference read from media files chooses this name.

The random 256-bit account master is stored under the independent named purpose `offline.master.v2`. Protected names use a non-UUID Keychain account attribute prefix; SessionVault's UUID-only credential API cannot address them. Writable legacy `key-reference` files are ignored. A 32-byte unrelated session credential therefore cannot substitute for the master. The object checkpoint stores pending/current/tombstone state, the exact encrypted index digest and a wall-clock high-water floor. Checkpoints contain no encryption keys. Missing authority and legacy valid GCM records fail closed on open; reading cannot enroll them. Explicit authorized `retain(file:grant:)` can replace legacy, replayed, expired, deleted or interrupted media with freshly imported bytes and a new object revision. `updateGrant` requires an already authoritative index; interrupted enrollment requires a fresh authorized retain.

Every actual index open compares the captured encrypted index bytes against the current named Keychain digest before decrypting those same bytes. It does not check one file read and decrypt a second, potentially replayed read. The current checkpoint is loaded for every existing-object open; no authority cache exists. A negative filesystem absence check grants nothing and returns not-retained without a Keychain lease, preserving the independently licensed bundled-owned fallback. Any existing/restored folder still enters F1. A revoked current index continues to refuse after byte-for-byte rewriting. Restoring an older index or deleted folder fails against the protected digest/tombstone in the same instance and after a fresh process starts, with Keychain and clock unchanged. No operation rolls a pending checkpoint back to an earlier current one.

## Serialization and security commit order

All store opens, clear-byte delivery and file/checkpoint mutations take an exclusive account lease in Keychain. This conservatively serializes even different variants; stage A prioritizes the security boundary over throughput. SecItemAdd atomically admits one token. Other instances/processes wait cooperatively up to five seconds, then return busy. Only that token, the current account generation and exact account scope can read or replace protected records. Scope is checked again after suspension, before final publication and before native clear-byte delivery. Consumers execute while the lease is held. Ordinary reads are linearized before lease release, and scope/cancellation are checked again after release before returning a direct range result.

The lock records an owning PID and random token. A live or reused PID is never displaced. After a crashed process, ESRCH permits deletion of only the exact old token via a matching Keychain generic attribute; a competing replacement cannot be deleted by stale cleanup. An unrecognized/unavailable owner fails closed. A token can be released after detach, but release grants no read or write permission. Cleanup of an entire account also acquires this lease; active work returns a retriable busy error rather than racing wholesale deletion. macOS legacy Keychain account cleanup explicitly matches all records in that exact service scope, including protected records and orphaned UUID credentials. Other accounts are untouched.

Actual sequence, implemented in `commit` (also diagrammed in the stage-A evidence):

1. Acquire lease and validate the existing current index for normal mutations. Fresh explicit import may start from missing/pending/tombstone/legacy state.
2. For import, prepare encrypted chunks and encrypted index in a private staging folder. No published authority changes yet.
3. Persist Keychain `pending` with a non-decreasing trusted time floor, then recheck scope.
4. Atomically publish/rewrite the encrypted index, or delete the object. Fsync file and directory operations; recheck scope. Pending denies old and new file bytes during this interval.
5. For current state, verify published encrypted index bytes equal the prepared bytes, then persist its digest as Keychain `current`. For delete/final-unpin, persist `tombstone`. Only then return success.
6. Release the exact lease. Errors, cancellation, failed protected writes and process crashes never restore the old checkpoint. A pending state is recovered by a fresh authorized retain, not by opening old files.

A failure before pending has committed nothing and may leave the prior authorized state. A failure after pending denies access even if the old index/folder is restored. A crash after file publication but before final checkpoint also denies access. If final publication succeeds but its acknowledgement is lost, the actual protected state determines access; callers must treat the result as ambiguous and never roll back the checkpoint. Fresh imports preserve the protected time floor in their encrypted index, including restart timestamp round-trip differences. Whole-volume restoration of both Keychain and files, a hostile kernel, replacement of the application, or modification of Keychain itself remain outside this file-tampering model. Ordinary index/folder replay is inside the model and is rejected.

Production assumes one configured retained root and one lifecycle owner per account. Multiple store instances/processes using this Keychain namespace serialize their opens and commits through the same account lease. Lifecycle generation floors remain process/owner-local as in W04; separate independently authenticated lifecycle owners are not a distributed session service. Keychain lease recovery errs toward busy if PID reuse makes a dead owner ambiguous. Callers retry rather than bypassing the lock. A corrupt protected checkpoint cannot be repaired by trusting files; account cleanup and genuine reauthorization may be necessary.

## Existing container and reference behavior

Private account and variant directory names use SHA-256 of canonical identity/variant input. Source strings never become filesystem components. Reference sets and a separate manual pin bit share one same-account/variant object; mutation and final removal now advance protected authority. Metadata cleanup and integrity checks do not grant playback rights. Explicit grants require issuer, rights, validation time, expiry, renewal reference and source-encryption descriptor; no expiry/rights defaults or permanent/30-day assumption exists. Source adapters must establish those facts and an account-unique variant identity.

CryptoKit uses a fresh random 256-bit salt per record write, HKDF-SHA256, and a fresh GCM nonce. Account/variant/revision/chunk index and length remain authenticated. Import creates ciphertext-only staging; no cleartext temporary files or local HTTP server exist. Descriptor-relative openat/O_NOFOLLOW, ownership/mode/type/hardlink checks and fsynced atomic publication remain in force. Scoped partial cleanup now runs under the lease on protected access, not an unleased bind that might delete a concurrent live import.

Complete verification precedes local resolution and requested range delivery. A bounded eight-entry revision fingerprint cache tracks chunk inode/device/size/mtime/ctime; changed metadata forces full chunk authentication, and each requested chunk authenticates again. Plaintext range output is capped at 64 KiB, metadata input at 1 MiB, objects at 32 GiB, and native loader admission at eight requests. Framework buffers and metadata enumeration are additional costs. There is no whole-process performance acceptance claim.

The owned native asset seam accepts only the explicitly owned identity, items and authorization reference; its default file provider still rejects arbitrary network URLs. Optional retained-root construction failure can use only the independently licensed bundled-owned route. Actual retained rights/corruption failures do not become that init-only fallback. The provider owns weak AVFoundation loader delegates, so native tests retain it for the entire decode. Future source/network providers must deliberately implement their own authorization and native-asset seam; this owned test boundary is not a general source grant.

## Decoder byte access and user seek — stage B

A play+retain grant can fully decode the owned WAVE without seek. AVFoundation metadata probes and decoder reads may be nonzero/out of order; byte-range support is not a user-seek capability. Downloads' module-internal deliverDecoderBytes retains all current authority/time/play+retain/scope/chunk checks. Only semantic seek classification differs. There is no public ignore-rights flag. Public arbitrary read/deliver keep the seek requirement at nonzero offsets; offset-zero playback access remains available. Missing seek is seekNotPermitted/Domain forbidden, not a renewal request.

NativeAssetSession is a trusted preparation-owned provider handle containing an asset, observed userSeekable capability, fresh asynchronous user-seek authorization, a bounded first-failure stream and disposal. LocalFirstOwnedAssets checks current rights on each seek, including grant changes after prepare. Default file sessions honor variant seekability. Dynamic-rights or decoder providers must override assetSession and supply independent preparation ownership/cancellation; a URL or owned identifier is not a source grant. NativePlayer retains its file/exact-owned-scheme admission. Future network/source integration must add a verified admission contract deliberately, not bypass this guard or presume an arbitrary nativeAsset override authorizes a network URL.

NativePlayer captures full context, session/asset ID, operation, item and seek request before permission work and checks them again before native movement and after acknowledgement. Denial does not pause/move the native item. NativeMediaInfo.userSeekable is a preparation/last-validation snapshot, never cached authority. The timeline reflects it; command surfaces revalidate. Shared commands validate before establishing seek intent, restore its original position/intent when final native permission refuses, and return the error without stopping eligible playback. A resolving seek remains queued intent and is not applied without the final prepared check. Obsolete replies cannot stop/fail a replacement, including same-context reprepare. A coalesced scrub uses the same private seek application path without cancelling its own task; its handle remains cancellable by a newer scrub.

## Typed loader failures — stage B

A real loader refusal after successful preflight records the first typed Domain failure in its preparation session before cancelling native metadata loading. The event-driven NativePlayer monitor pauses/disposes the affected preparation and emits a scoped failed event. Pending prepare/seek results and native notifications prefer that same first failure over an AVFoundation timeout wrapper. Expiry/revocation/clock failure maps to expiredMedia, corrupt data to malformedResponse, and missing-key/owner invalidation to unauthorized. This does not fix F4's wrong intact-read storage behavior.

Cancelled requests are not source failures. Cancellation before a user seek is dispatched returns staleContext without moving the item; wrapped native URL-cancel errors are not fatal source errors. Stop/detach/replacement/Quit dispose the old session, loader requests and monitor. Late callbacks check cancellation/disposal after suspension; engine events also check operation/session/full context. No new steady timer is introduced. Native position/status observations retain capture timestamps from the shared clock before actor delivery. AVAssetReader/nativeAsset callers must retain their provider until decode ends; that legacy route retains at most two sessions. Engine callers own/dispose the session directly.

## Stage C: complete local rework contracts

Retained reads no longer rewrite/fsync encrypted index files. Every range still acquires the exact-account Keychain gate and loads current protected authority; authorization is never cached. Only a master SymmetricKey is cached, at most one active-account entry for one second. A Keychain attributes-only version/presence lookup precedes every reuse. Replacement/deletion of that protected item, owner/generation change, expiry, explicit disposal or the one-shot idle expiration invalidates it. Legacy protected items lacking a version remain uncacheable. No material is returned by the version lookup, and no claim of zero Keychain calls is made. Native disposal requests cache teardown; expiry bounds idle retention even without another read. There is no playback-long protected lease.

Completeness/fingerprint and integrity-hash work is sliced: at most 64 work units or 50 ms of cooperative work per gate acquisition, plus a currently executing filesystem/Keychain call whose OS latency cannot be preempted. Incomplete validation releases/reacquires authority and yields, checking the current scope/grant/time again. Payload reads remain at most 64 KiB. Successful writers in another instance/process therefore precede the next authorized delivery, not a stale cached license. Fingerprint/validation/hash state remains bounded at eight revisions each. A changed requested chunk is always authenticated before release. Standard inode/ctime filesystem semantics and the existing hostile-kernel/whole-Keychain rollback exclusions remain; no atomic snapshot of a hostile filesystem is promised.

Trusted time is an account Keychain record, independent of writable media. It advances monotonically on read admission at most once per second; security commits retain their per-object floor too. Crash recovery can lose at most that one-second observation interval, in addition to the documented two-second wall tolerance, never a committed floor. It does not extend the grant's explicit expiry. An observed wall/monotonic discrepancy sets a protected sticky blocked state; reopening/restarting, retrying updateGrant, or replaying a file does not clear it. Expired grants observed under a consistent clock advance trusted time before refusing. Revalidation preserves the maximum prior floor and maximum validation time even if an ordinary grant update supplies older fields.

The explicit revalidate(variant:grant:sourceTime:context:) API is the only anchor-recovery path. Its adapter MUST authenticate a genuinely fresh source-time observation and bind it to a genuinely new grant; passing a local Date or repeating an old grant is not valid evidence. The API requires strictly newer validatedAt than the object observations, source time at/above the protected floor and previous anchor, a live play+retain grant, and agreement with local wall time within two seconds. Only after protected security commit and healthy time-state persistence does it adopt new monotonic/wall anchors. Backward-below-floor time cannot recover until a genuine source observation and local clock meet that floor; the floor is never lowered. If a jump was never observed while the process was alive, later wall time at/above the floor is indistinguishable from legitimate elapsed time; the API cannot certify hardware time or defeat whole Keychain+clock rollback. Actual service-time proof remains W36, not a fixture claim.

Import preparation now runs on a detached utility task, one encrypted 64 KiB chunk/fsync at a time, with cancellation and actor ownership/grant-expiry checks between chunks. No account lease is held during bulk work, so existing reads and detach progress. The source descriptor is no-follow regular/single-link and bounded at 32 GiB; final size/inode/device/mtime/ctime must match its initial snapshot. A private staging descriptor/flock protects live work from other instances' cleanup; process death releases that lock. Cleanup and publication check descriptor identity so an old task cannot remove a replacement folder. Same-instance same-variant requests queue cooperatively; other writers are reconciled at the protected publish boundary. An intervening grant/reference/pin/delete security revision or master-key change rejects the stale prepared import. Time-floor-only updates do not manufacture a false content revision. Publication still uses pending/current/tombstone, a current owner check and verified atomic encrypted-file publication; no partial cleartext exists.

Detach cancels workers promptly. Full account removal waits for those bounded workers to stop, then performs private cleanup while the Keychain account gate still exists and only then erases exact-account records. A newer generation invalidates stale cleanup. Another process cannot recreate data between key erasure and old file cleanup. Explicit writes to an intact 0500 data directory fail as storageUnavailable before claiming a security commit, while ordinary authorized reads/decodes continue. A real later disk or protected-write failure after pending remains fail-closed; none is silently swallowed. ENOSPC remains distinctly classified but no physical full-volume experiment is performed.

The actual owned composition now has deterministic held-teardown controls: old quit/detach cannot clear a newer retained-store assignment. Unsafe optional root construction uses only the independent bundled-owned license and is tested through native prepare/full decode. Actual retained revocation/corruption is refused rather than silently falling back. Read-only internal engine/provider inspection is used by headless tests; no production UX/test button or audio autoplay is added. The provider/native admission overrides remain trusted integration seams, not proof that any owned-scheme URL has a loader or entitlement. Locked production Keychain mutation behavior stays unobserved; only supported noninteractive queries and isolated unlocked test Keychains are exercised. All G01–G09 remain open for the larger release contract.

## Rework 2: credential erasure, time authority and ordered callbacks

This section supersedes earlier accounting/time/lease descriptions. Session credential erasure no longer waits for an offline lease. W04 signOut/remove first deletes exact-account UUID credentials and writes a durable erasure epoch independently of the offline gate. Protected reads/writes bind their lease and Keychain item purpose to that epoch; a successful erasure invalidates an old writer and cached material without deleting a genuine live writer's lock. If remove cannot obtain the private cleanup gate, its removalPending record permits retry; session credentials are already gone. signOut does not create that removal retry record. Fresh authenticated insertion binds a new authorization epoch; an erased account cannot silently re-enroll protected records through its old context. Private cleanup retains the account gate until files are gone and erases only the exact scope. Matching-token release remains safe after detachment. Independent distributed lifecycle ownership is not introduced.

New lease owners record boot-session UUID and kernel process start time as well as PID/token. A record with the same live PID but a different incarnation can be reclaimed by exact token; a genuine current owner cannot. Dead-owner recovery remains supported. Legacy live owners lacking an incarnation are conservatively unprovable: offline cleanup can return busy within the admission bound rather than blindly stealing a lock. This does not block credential deletion or retain old read/write authorization after erasure. Locked or denied Keychain operations can still fail; failure/tombstone status is reported, not relabelled complete. Only isolated unlocked Keychains were tested; no ACL, lock/unlock or authentication experiment was performed.

Clock state now separates unauthenticated local observation from authenticated source time. Ordinary read/expired-refusal observations may raise an observed floor but never become source authority. Accepted source grant validation timestamps and explicit authenticated revalidation advance the source floor monotonically. A fresh source observation may correct a poisoned observed floor and establish a new protected recovery epoch; old per-object/index observed floors do not keep unrelated objects or new variants poisoned. The authenticated floor and callback-validation ordering are not lowered. Corrected wall time/restart alone still does not clear a detected fault. Source-time revalidation remains a trusted W36 adapter contract: fixture Date values demonstrate rules, not live proof. Old/stale/below-authenticated-floor receipts refuse across restart and across objects.

updateGrant refuses timestamps older than the protected maximum. Identical equal-time callbacks are idempotent. Equal-time observations can only become strictly more restrictive (rights subset and no longer expiry); an equal-time permissive or otherwise conflicting update requires genuine source ordering and refuses. A genuinely newer valid observation may restore permission. Synthetic upgrade fixtures use ordered past/current validation observations rather than moving validatedAt into the future or removing denial assertions. Fresh retained import remains an explicit separately authorized operation, not permission inferred by opening files.

"0 file writes/fsync" in earlier decode observations refers ONLY to app-managed media/index files and the explicitly instrumented app filesystem calls. Each protected range still uses SecItemAdd/SecItemDelete for a persistent Keychain lease, and those mutate the Keychain database even with recordWrites=0. Keychain API counters now expose lease add/delete calls separately. Playback therefore depends on writable/unlocked usable Keychain services; a lease/protected write failure refuses access (busy/Keychain error, or the existing coarse native transient category), not a fabricated offline success. Neither zero durable I/O nor locked-Keychain no-UI mutation behavior is claimed. Representative cost/energy belongs to W44.

Owned test loader gates and subprocesses are bounded. A gate watchdog records an assertion and releases owned continuations; native replacement/disposal then proceeds. Owned subprocess watchdogs supervise only the explicit Process PID, request normal termination then kill that PID if necessary. No global name matching, source permission weakening or production timeout change is used. The Opus02 terminated rights plant remains INVALID/incomplete in its original archive; a new focused plant must finish through assertions to count. Play-only Previous/restart remains a later UX/W15/W36 policy: it must not gain seek implicitly. No speculative stale-event Domain rewrite is included.

## Rework 3: all-entry grant ordering and remaining obligations

Every actual grant installation uses that item’s protected validation maximum. The account authenticated floor bounds source/clock time, not receipt order across items. Import setup checks ordering before bulk work, and publication checks it again while holding the account gate. The captured object revision must still match; a newer revoke/delete/reference decision during work wins. Pending and tombstone checkpoints preserve the validation maximum and full grant history through failed file/current commits. No file or ciphertext enrolls history. A current equal-time callback may be identical or strictly restrictive with unchanged issuer/encryption/renewal identity, a rights subset and no later expiry. Unknown history, pending or tombstone recovery requires a newer object observation; a missing checkpoint beside existing files cannot establish equal-time trust. A genuinely newer observation for an object may predate another item’s receipt. Healthy retain only adds its reference and preserves the authoritative grant, including when a queued job carries an older receipt.

Ordinary updateGrant refuses validatedAt later than the injected/local wall clock as renewRights before loading the index or changing its clock/floor state. It does not substitute local time for source time or set a sticky discrepancy fault. A subsequently now-valid ordered update can succeed normally. Retain checks this timestamp before preparation and again during work/publication. Explicit authenticated revalidation retains its separate two-second source/local agreement contract; actual source skew/proof policy belongs to W36.

SignOut under a held offline lease erases session credentials and logically revokes old protected rows using the erasure epoch. Old-epoch master/checkpoint/clock records may remain physically present, unreachable to authorized app access, after lease release and re-sign-in. There is no signOut background physical-deletion retry in this delivery. Only remove has removalPending/retry. Logical fencing is not evidence of physical Keychain erasure. The late unscoped credential-refresh re-enrollment composition obligation remains W04/real-auth work and is unobserved here. No credential/process/OS experiment or new cleanup scheduler was added in this continuation.

Persistent Keychain I/O remains material: the reviewed observation included about 727 lookups for a full fixture decode, with lease add/delete (two persistent mutations) per range. Zero app-owned media/index writes is not zero durable I/O. Playback requires usable writable Keychain services; locked-Keychain mutation/no-UI behavior remains untested. Representative performance/energy is W44. Play-only Previous/restart policy remains W15/W36 and does not gain seek implicitly.

This narrowed continuation uses ordinary synthetic ordering/integration checks. It does not run deliberate guard-removal builds or a new mutation campaign. Earlier preserved invalid/terminated attempts remain so classified. Independent review and any outstanding acceptance controls are required before parent adoption. W14 and all G01–G09 remain open; fixture timestamps/permissions do not supply live source rights, encryption or time.

## Rework 4: item ordering versus account time

This corrects the withdrawn cross-item floor requirement in rework 3. Installation, renewal and explicit revalidation order validatedAt against only the item's protected history. B's later receipt does not stale A's otherwise valid receipt, even when A finishes its import later. SourceTime during explicit revalidation must still meet the nondecreasing account authenticated time floor and local/source agreement; expiry, local future refusal, sticky clock recovery and scope fences remain independent. Pending/current/tombstone histories and conservative equal-time rules remain per item. The captured revision/key/scope publication check still rejects a held import after a newer same-item decision.

Ordinary S1–S5 tests exercise out-of-order installs, concurrent completion, renewal, held same-item revocation and explicit revalidation across items. The earlier new-item staleOther negative expectation was erroneous and is superseded by a positive install assertion, without weakening stale-same-item, tombstone, equal-time or future-refusal assertions. No changed-guard builds or new fault campaign were performed. Sign-out physical-remnant, trusted-provider, locked-Keychain, W15/W36 and W44 limitations remain as above. All release gates remain open.

## W15: scheduling and the Downloads screen

The durable download scheduler, quota/retention policy and the Downloads screen consume this store through `RetentionSink` (`EncryptedStoreSink`): one `retain` per finished download, references named `manual`, `smart` and `collection:<id>`, the pin for manual downloads, `updateGrant` for renewal, and `delete` on removal. See `Docs/Downloads.md`. The store itself is unchanged by W15. YouTube Music items are never retained (no permitted route; `artifacts/harness/W15-offline-source-decision.json`); the source seam stays for owned/local media and for any source that states an explicit permission. W36 still owns authorized-source grants, source-time renewal and the playback side for non-owned retained media.
