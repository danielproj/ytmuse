# Local persistence

`SQLiteStore` is an actor in the existing Persistence module. It implements Domain's `PersistenceStore` and `MutationOutbox` contracts. The app composition and account lifecycle attach this implementation in their assigned nodes; no fixture store is attached to the welcome screen. Apple ships SQLite; there is no new runtime or package dependency.

Each identity partition includes local account UUID, channel and region, with length-framed keys. All private catalog, collections, queue, history, membership, downloads, artwork and outbox tables reference the identity partition. No private metadata is deduplicated across identities. Public sharing can be added only with independently verified public provenance. `bind` is for the trusted session owner after generation invalidation. It retains an account-generation high-water mark for this store lifetime: older bindings are ignored, and an equal generation can only retain the same account/channel/region owner. A newer generation is required for identity changes, including sign-out and switch-back. Removal clears the active owner without discarding that high-water mark, so delayed or duplicate removed-owner bindings cannot resurrect access. Closing permanently prevents rebinding. A fresh store may bootstrap at any generation, including zero; generations are not persisted across session-owner lifetimes. Per-feature query generations may arrive in either order for the accepted owner. Every operation checks account identity and account generation; request generations do not alter the storage namespace. Removing a partition cascades rows, including its FTS documents. Window/global preferences are device state; account preferences use the same partition key.

Entities and membership, collection occurrence ordering, queue occurrence ordering, download ranges/references, history and outbox are separate tables. Small typed metadata records use versioned-schema JSON codecs owned by Persistence, never raw provider JSON. FTS5 uses Unicode tokenization and diacritic removal with literal prefix terms. Case/diacritic/prefix search is local and account scoped; it makes no completeness claim about the service. SQLite binds every input. Library and collection pages use indexed keyset queries. Public page sizes are 1–200; ingestion batches are at most 1,000. Search inputs are at most 512 UTF-8 bytes. Metadata records are at most 64 KiB. Collection pages preserve provider or synthetic occurrence identity independently of media identity. Collection ingestion fails atomically on conflicting occurrences/ordinals rather than replacing an unrelated occurrence.

The command owner can restore a whole bounded queue (maximum 100,000 entries); views use the 200-entry maximum `queuePage` and `recentHistory` APIs. The stress fixture exercises a 5,000-entry queue. Queue header, version, selected occurrence, sampled position, shuffle seed (including full UInt64 range), repeat, autoplay, context reference/cursor and entries/consumption commit together. `checkpoint` retains continuation references. Restore always supplies paused intent. Process-local monotonic anchors and entitlement leases are never serialized. The playback owner samples position using the injected monotonic clock before checkpointing; wall time is for history/server expiry. Offline authorization still requires entitlement validation, with backward-clock rejection and monotonic expiry; a restored position grants no rights.

WAL allows bounded readers while other connections checkpoint or claim work. `synchronous=FULL`, foreign keys, secure deletion, a 5-second busy timeout and a 1,000-page automatic WAL checkpoint are enabled. The private connection uses SQLite's no-follow mode. Darwin `realpath` canonicalizes the parent because Foundation's URL canonicalizer preserves macOS's `/var` alias; the final database path is never symlink-resolved. App directories are 0700; database, migration lock and sidecars are 0600, owned by the current user. File creation refuses symlinks and hard links. This protects against other local users; metadata is **not encrypted**. It is not a claim of protection from another process running as the same user.

## Migrations, backups and recovery

On open, an exclusive process file lock serializes migration attempts. SQLite serializes writes across open connections. Supported migrations run in one `BEGIN IMMEDIATE` transaction and advance `user_version` in that transaction. A thrown error or process kill rolls back schema and content. Versions newer than this implementation fail closed; no database is reset or erased.

Before upgrading an existing schema, check at least 16 MiB or three times the logical database page size (including the committed WAL view) is free, whichever is larger, then take an online SQLite backup named `backup-v<oldVersion>-<UUID>.sqlite`. The backup API produces a consistent snapshot including committed WAL data. The explicit backup API applies the same space reserve. Backups switch to DELETE journal mode so each is a standalone file. Integrity and foreign-key checks verify each copy. A migration error keeps both the old schema and the versioned backup. Rollback is the automatic restore mechanism; retrying a fixed migration does not require destroying data. OS-level power-loss durability is supplied by SQLite and the filesystem; tests use actual SIGKILL, not a physical power cut.

`backup()` is an explicit local administrative operation and can capture all partitions. Backup metadata is as private as the live database. Do not export it as diagnostics. `SQLiteStore.recover(backup:into:)` validates integrity, supported version and required structure and checks free space, then copies into a **new** 0700 directory. It refuses an existing destination. The session owner may explicitly select that recovered directory after closing the old store. The original database and WAL remain available. Corrupt backup input fails before a destination is created. A copy failure leaves its separate partial destination for inspection, never deleting the original library. Open the recovered store normally to finish any needed migration. This is an explicit recovery API, not a wipe-and-rebuild fallback.

Backups are retained until explicit user cleanup; there is no automatic destructive backup pruning in this node. Account removal scrubs that partition and its preferences from every app-managed backup, rebuilds FTS to remove deleted terms, and runs VACUUM. It applies the same deletion/index rebuild to the live database, compacts it and truncates WAL. A busy checkpoint reports an error so the session owner can close readers and finish cleanup. An unreadable backup produces an explicit removal error rather than claiming privacy deletion succeeded. Account/Keychain/file lifecycle orchestration remains in W04/W14/W27; this API makes no remote deletion request. Metadata cache retention and source cache expiry are enforced by the owning feature adapters; `noStore` artwork removes its metadata record. Retained history is cleared by explicit provenance/account and optional wall-date boundary, so clearing local history does not imply remote history deletion. Queues, pinned media and other identities are unaffected by preference resets/history clears. Media encryption and disk quota scheduling are separate W14/W15 work.

## Outbox and secrets

The outbox stores structured user intent, target, operation UUID, provider/local preconditions, attempts and outcome. The operation UUID is globally unique. Re-enqueue accepts only an identical immutable payload and returns existing status; a differing payload/precondition/account fails. A first attempt uses one conditional UPDATE inside a transaction; exactly one connection can change attempts from zero to one. It commits `needsReconciliation` **before transport begins**. Crash after claim, lost response or repeated dispatch requests cannot claim again. Cancellation retains a tombstone. Confirmed/failed operations also retain their UUID. Account removal deliberately deletes those operations; a session owner must never replay removed-account work.

`reconcile` records the need for a provider read; it cannot claim remote success. `commit` is called by the command/provider layer only after verified remote confirmation. This storage layer never transmits requests or automatically retries a non-idempotent operation. A reconciled replacement action must have a new deliberate operation ID; adapter-specific safe retry policy belongs to W07/W13. This conservative boundary may require user recovery after a crash just before transport, rather than risking duplicated additions.

There are no credential, cookie, header or signed-URL blob columns. The account credential field accepts a UUID addressing a Keychain record. Media records store opaque IDs and artwork references, not playable URLs or signed authorization. Metadata validation rejects common authorization markers, signed/token query parameters and URL credentials; errors expose only categories. Content scanning cannot identify arbitrary opaque secrets, so callers must preserve the typed reference-only boundary. Credentials stay in Keychain/ephemeral memory; this API must never be used as a generic credential store. No ordinary diagnostic logging is emitted by Persistence.

Run `./scripts/test.sh --suite T03`. It builds a separate synthetic native crash worker from the same persistence sources without changing the production target graph, checks nonempty test discovery, and runs storage tests. Only disposable synthetic stores are killed, corrupted or migrated. T02 preserves the accepted domain regressions.
