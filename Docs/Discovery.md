# Discovery extras and social workflows (W20)

Samples, the music tuner, Recap, badges, and comments / ratings / invitations / moderation. This node was built **source reality first**:
each feature was checked against the real public YouTube Music captures on `main` before any UI was built on it. Where a source surface is
present the app uses its real shape; where it is absent the affected place says so plainly and offers no control that pretends to work.
Live verification of every route is W38. Nothing here is live evidence.

## Previews and Samples (DISC04, T20.1)

`PreviewArbiter` (Features/DiscoveryExtras) is the one place that decides what previews:

- one clip previews at a time; asking for another stops the first and waits for it to be silent before the second starts. Requests are
  carried out strictly in order; a request a newer one overtook does not start (scrolling quickly leaves exactly the last clip);
- a preview that starts by itself (`autoplay`, from focusing a clip) obeys `PreviewPolicy`: refused on Low Power Mode, on a constrained or
  metered connection, when the person chose Off, and when something else is playing. A press on Preview is never refused by the policy. When
  the conditions turn against an automatic preview it stops; one the person asked for continues. The choice (`Automatic` default, `Off`, `On`)
  is kept for the session only; where it is stored belongs to Settings (W27);
- **Play** stops the preview, waits for silence, and only then asks the shared playback session to play the clip's own item, with the
  playlist and parameters the clip carried (`SearchActionPerformer.play`, the same path Search and the Library use);
- nothing starts at launch, on load or on sign-in. An account change stops the preview and discards a start that was in flight.

In the application a preview is the clip playing in the **one shared playback session** (`SessionPreviewEngine`): the hidden player already
owns picture and audio (W17's single-owner surfaces), so there is no second player and nothing can overlap. Stopping pauses that same player,
and only while it is still on the previewed clip. A previewed clip is reported to the local history as a preview, never as a play. The device
conditions come from `ProcessInfo` (Low Power Mode) and a passive `NWPathMonitor` (`isConstrained || isExpensive`); the monitor sends nothing.

A preview is one clip. Played through a radio, a clip would run on into the radio's next tracks, so the preview is watched (`PreviewWatcher`): it ends at the clip's stated length or when the player reports the clip ended, a player that ran on into another item by itself (nobody asked it for one since the preview began) is paused, and a player that moved because something else asked it simply stops being previewed. Only an explicit Play continues past the clip. A preview shares the one player, so pressing Preview while something plays replaces it (the Samples screen says so); Stop pauses rather than restoring what was playing. When a source supplies clips, the previewing row shows the picture in W17's single-owner inline surface (`WebVideoPreview` over `VideoSurfaceOwnership`), or that surface's placeholder if another surface holds it.

Because no source route for Samples exists, **no preview can start in the shipping app today**; the arbitration is exercised end to end
against scripted engines and, in Debug UI runs, against labelled development data.

## Tuner (DISC03, T20.2)

`TunerModel`: seeds → explicit start → context → metadata controls. Seeds retain the service’s own start endpoint. Production now reads the radio queue through the R1 reader and presents the published filters; read failure is retryable, distinct from a successful response with no controls. Metadata retry does not play anything.

Canonical chip selection updates the section of the existing radio’s queue that the chip names, through `SearchActionPerformer.applyRadioFilter` and the official page’s `resolveCommand`. A captured scope binds the controls to the existing owner, document/load and current radio content; account replacement, another start, local media or a replaced document invalidates it. There is no owned-start permit, engine handoff, held start, cookie installation, document creation, current-item/artwork reset or forced resume. Native queue admission and immediate page-side ad detection refuse unsafe dispatch. The exact bounded command preserves `watchEndpoint`, params, optional playerParams and the published section/dedupe/sync constants; there is no invented URL mapping. Legacy performers refuse it rather than dropping fields.

Router acceptance alone is unconfirmed. A bounded control-specific wait requires a fresh ordered upcoming-video change for the applicable current content, while allowing the original playlist/video and paused state to remain. Timeout or absent evidence reports an unconfirmed control without failing healthy playback. The metadata read uses the selected published fetch target and its params/playerParams separately from the unchanged active playback scope. Fresh metadata selection flags remain authoritative; the requested choice never overwrites them. This is conservative: a service-applied filter with no later readable queue change remains unconfirmed. Ordinary endpoint and genuine Shuffle confirmation retain their existing contracts.

R1 and R3 artifacts record the frozen capture, source changes and Release/static checks. R3 regression sources have only been syntax-parsed, not executed. Normal signed-account filter loading/application was subsequently accepted by the account holder on 2026-11-05. Exhaustive queue/report timing, per-filter edge cases, native layout/accessibility and W38/G01–G09 acceptance remain deferred beyond the accepted working core. Historical W20 reports describe the earlier unresolved implementation and remain historical evidence.

## Recap and badges (T20.3)

`AccountSummaryModel`. Entries are the source's own text (`SummaryEntry.value` is never parsed, rounded or summed). A payload with no
entries is `payloadMissing`, not an empty Recap.

**Recap, signed service-message reader (MORE-FEATURES).** One bounded read of the known handler (`MusicRecapRoute.browseID`, `FEmusic_listening_review`) through the existing signed `browse` path (`SignedMusicClient.recap` → `MusicSessionCoordinator.recap`, which is `scopedSigned`: signed only, account-generation fenced, credential rotation saved like every signed read). No endpoint, host, write allowlist or OAuth scope changed. An explicit screen open or Retry is at most one request; there is no startup read, prefetch, polling or retry loop. Signed out, nothing is sent (`signInRequired`). `MusicRecapParser` accepts exactly the captured envelope and nothing else:

* the response must prove it is the Recap handler (`GFEEDBACK.browse_id`) and state `logged_in` (`0` → needs sign-in for the pure parser and a signed-out session for the signed read, `1` → continue; absent or other → unreadable);
* `contents.singleColumnBrowseResultsRenderer.tabs` with exactly one tab whose content is exactly one `messageRenderer` → a **service message** (`SummaryState.serviceMessage`), its text read at run time from `messageRenderer.text` (`runs[].text` joined as printed, the only representation captured; a run that is not an object with a string `text` makes the message unreadable), never trimmed, reworded, localized or marked up, bounded (1,000 UTF-8 bytes, 16 runs, no control characters other than line breaks and tabs; over the bound is refused, not truncated);
* failures follow the signed client's existing mapping: HTTP 401/403 or the explicit `loggedOut` flag or `logged_in=0` end the session (`signedOut`: the identity expires, "Your session ended"); 429 is `rateLimited` (the pause message); 5xx is `server` ("couldn’t be read"); an oversized body is `oversized`; everything else — other HTTP statuses, non-JSON or malformed bodies, an error body, another handler, a missing or odd `logged_in`, contents with any other renderer, a second tab, an empty or unreadable message, `simpleText` (never captured), a future successful payload — is `MusicSessionError.unrecognised` → "couldn’t be loaded" with Retry. Never empty, never computed.

While the Recap screen is **open**, an account or session change (switch, reconnect or expiry all change the source token) starts it over with at most one fresh read for the new scope; a signed-out or expired scope sends nothing. No startup read, no polling, no retry loop. A service message is its own state: not `payloadMissing` ("nothing to show"), not `accountUnsupported`, not evidence that the account has no Recap. The captured message's words are unknown (the export replaced them with placeholders), so the screen says only that YouTube Music sent a message, shows it verbatim and says the app cannot tell whether it is about the account or a temporary problem. **A successful Recap summary still has no evidence; no parser for one exists.** The captured message also nests a secondary text under two keys the export redacted; their names are not evidenced, so nothing under them is interpreted and the secondary line is **withheld** until a capture shows it. A signed read the service answers as `logged_in=0` is `MusicSessionError.signedOut`, so the coordinator expires the identity like any other signed read (the pure parser still reads the anonymous capture as needs-sign-in, and there is no anonymous fallback). Badges keep their own unresolved reason (`recapUnresolved` / `badgesUnresolved`) and Samples are unchanged; `LocalListeningSummary` stays a separate, never-official "On this Mac" record. This Mac's own record (`LocalListeningSummary`, from the local history) is a separate
property on its own screen under its own title, **On this Mac** (an Explore entry of its own, not part of the Recap screen), labelled "not YouTube Music's Recap", `isOfficial == false`, and never fills a missing Recap.

## Comments, ratings, invitations, moderation (MEDIA10, T20.4)

`SocialSurface` rules: every write is one explicit call for one item; `SocialPolicy` decides the role before anything is sent (signed out → every write denied, but reading comments needs no account; only a playlist's owner may invite or close contributions, from the rights the playlist published); moderation is offered only where
the source offered that exact action **on that exact comment**, and a destructive one needs the confirmation the question named (`ModerationConfirmation`: which offer, on which comment, by whom, saying what — compared with what the page shows now); the comment list is only ever what
the source returned (a confirmed post is shown by reading again, never by inserting text); an unknown outcome — including a reply to a sent request that could not be read — is shown as unconfirmed, read back before anything is sent again, and never retried by itself; "nothing was sent" is said only for offline, signed-out and ended-session failures. Every action leaves one `SocialOutboxEntry` with its result (`pending`, `confirmed`, `failed(sent:)`, `unconfirmed`,
`denied`, `sourceUnresolved`) and whether anything was sent. A transport takes a `SocialSubject` (a service id), never an address, so there is no
path to read arbitrary external comments (`W20SourceGuardTests` sweeps for it). Ratings and invitations are written only by the Library ledger
and the playlist edit session; the like and dislike buttons run the role check and outcome record (`SocialSurface.rate`) around the button's own ledger call, so the ledger's single submit call site is unchanged; the app still has the single `awaitedMusic().write(` call site.

## Comments reading flow (MORE-FEATURES C3)

**What is implemented.** `SocialSurface` reads comments through a `CommentsTransport` that takes a `SocialSubject` (a service id) and, for a continuation, an opaque `CommentsToken` the service issued — never a URL or a string address. Production composes `CoordinatorCommentsTransport`, which resolves the coordinator **for every request** (never a coordinator captured at start-up) and maps its C2 answers; isolated automation composes `UnresolvedCommentsTransport`; the Debug-only development flag composes the labelled `ScriptedComments` ("Development data · Not YouTube Music").

**States** (`CommentsState`): `unresolved` (no read route), `idle` (nothing asked yet), `loading`, `loaded` (header with the printed count and the service's own sort titles, threads, inline and read replies, printed like and reply counts), `notOffered` (no Comments tab, or a playlist: no request is sent for a playlist), `serviceMessage` (the tab's own message, carried verbatim and only from the transport) and `failed` (offline, rate-limited, unreadable, or *out of date*: the list was replaced and the comments are shown again). An empty page is `loaded` with no threads, never `notOffered`.

**Explicit actions only.** Show comments (≤2 requests), sort (1), More comments (1), View replies / More replies (1 per press). A press while the same read is loading sends nothing. A sort switch drops the old order's in-flight more/replies answers; an account change drops every in-flight answer (`generation` and a per-subject counter; one context per song id, so a retitled subject is the same context). A failed sort keeps the old order; a list the coordinator replaced offers only "Show comments again". No avatar is loaded and no link is activated; the text is shown verbatim.

**Bounds.** 10 pages per sort order (the first counts) and 5 reply pages per thread, stated in the panel when reached.

**Writes are unresolved.** The transport protocol has a separate `writesUnresolved` (non-nil by default). While it is non-nil there is no composer, no moderation menu, and every post or moderation is refused by the surface — "Posting and moderating comments aren’t available from this app yet." — before any transport call. This is the app's own state, not a claim about what the service offers. Only the labelled scripted development transport (and test fakes) say they can write.

**Limits.** Fixture-tested against the real anonymous captures' shapes through the C1/C2 parser and transport; the UI is compile-checked only. **Not verified:** the live app, a signed account (signed shapes were never observed), any real post or moderation, native UI, hardware.
