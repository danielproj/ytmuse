# Local occurrence queue

W05 implements the local queue domain, command owner, persistence adapters and feature state. Native media still goes through `Domain.PlaybackCommands`; the queue never resolves streams, directly controls an engine, creates a remote playlist, or claims cross-device synchronization. The recording and held providers in QueueTests are synthetic test boundaries, not YouTube or AVFoundation evidence.

## Occurrences, segments and edits

Each appearance of a song has a UUID independent of its media ID. `currentOccurrence` selects one appearance independently of its provenance. Upcoming segments are Play next, source context, Add to queue and recommendations. The legacy `.user` segment remains an explicit addition for stored compatibility. Advertisements and immutable service occurrences retain separate restrictions.

Play next inserts in selection order before all pending additions; a subsequent insertion takes precedence. Add appends before recommendations. Move accepts occurrence IDs in selection order and a destination occurrence, shared by keyboard and drag bindings. Moving a recommendation promotes it to an explicit addition; the end destination is the end of the deliberate sequence. A move cannot cross a protected slot. Remove and clear preserve current, consumed and immutable entries. Selecting a later ordinary occurrence consumes skipped ordinary entries without manufacturing listening history; it cannot skip pending immutable source items.

## Context starts, shuffle and preferences

Starting a different context asks if explicit pending additions exist and the advanced preference is Ask. Keep places pending Play next immediately after the new current and other additions after the remaining new source. Replace discards pending ordinary additions. Pending immutable service items block context replacement, so changing an album cannot bypass required ads.

`startContext(..., start: .shuffled(seed:))` atomically permutes the entire new context and chooses its first occurrence from that permutation. A normal `replace` preserves the enabled shuffle seed and applies it to the whole new context. `.ordered` explicitly starts at source item one and disables shuffle. These follow the existing Play/Shuffle and reversible shuffle contract; they introduce no new user preference.

Toggling shuffle during playback only permutes eligible context slots, preserving the current occurrence, consumed slots, explicit additions and service protections. The deterministic algorithm is SplitMix64 with Fisher–Yates. Disabling it restores the original order of eligible context occurrences. Consumed shuffled originals remain in their exact slots with their flags; they never return to upcoming.

`QueuePreferences` stores Ask/Keep/Replace independently of the queue checkpoint. `SQLiteQueuePersistence` implements it with the existing account preferences table, key `queue.replaceExplicit`, scoped by full account UUID/channel/region. Its read merges with other preference values on write. Default is Ask. A remembered context decision and the `.preference` settings command use this boundary; metadata only mirrors the current setting for rendering. Encoding a queue envelope writes Ask in that compatibility field. Restore reloads the authoritative setting even if another writer replaced the queue continuation. Settings rendering belongs to W27. In-memory tests can inject a shared `MemoryQueuePreferences` with the same scope semantics.

## Repeat, autoplay and intent

Repeat modes are Off, One and All, subject to injected verified support. One never repeats an immutable ad; All never resets advertisements, historical contexts or recommendations. Unknown service support must not be passed as permission.

Autoplay defaults on only where supported. A provider supplies actual recommendations and their source context; the queue fabricates none. Adjacent equal media IDs are omitted, including the deliberate/autoplay boundary and the most recently ended media after exhaustion. Disabling autoplay removes only unplayed recommendations; current, consumed and explicitly promoted entries survive.

Natural exhaustion retains active `.play` intent with no current item, so a late recommendation or user addition can continue without depending on provider timing. It does not invent listening or advance an empty queue twice. Explicit queue user/route/account/quit pauses cancel that continuation and invalidate old tokens. A passive Domain pause cancels continuation while retaining completion identity for the same live engine generation; accepted Domain play/wake observations restore active intent. A cold restore is always paused, including a checkpoint taken while waiting for recommendations. Late arrivals then stay upcoming until an explicit Resume. The lifecycle seam also accepts a current, scoped pause from the just-exhausted engine without allowing its old position to overwrite a newer occurrence.

## Commands, binding and resume

Queue edits and explicit queue transport use `QueueCommands.execute(_:context:origin:)`; Domain-owned passive transport is reconciled through the lifecycle sink below. A FIFO gate covers only local preference/checkpoint transactions. Commands arriving during that transaction wait their turn, then apply to the published state; they are not dropped. After commit, the gate is released before playback dispatch awaits capability, eligibility, source resolution or engine work. Edits, position checkpoints and valid end events can proceed while playback selection is suspended. A failed storage commit retains the old queue and undo stack and dispatches no selection. A failed post-commit selection leaves its occurrence identifiable for Retry and reports the error.

Every selection, repetition, explicit queue resume and explicit queue pause rotates a queue token. Passive same-generation Domain pause/resume observations retain it. End/checkpoint events carry that token so delayed work cannot advance twice or overwrite a newer position. The dispatcher checks that its token and play intent are still current, and ignores a superseded dispatch's error instead of publishing an obsolete snapshot. `QueueState` accepts concurrent sends, tracks outstanding work, refreshes from the owner after success or error, and exposes committed current/prompt/error state. Reveal uses `currentOccurrence`, even if playback failed after the queue commit.

The production `PlaybackQueueBoundary` forwards only permission-aware Domain commands. Production queue dispatch uses the versioned snapshot overloads: one boundary belongs to one request owner, accepts strictly increasing committed queue versions, and rejects older/equal arrivals before touching Domain. Snapshots must come from that single command owner, not synthesized callers. The entry/token overloads remain compatibility seams for injected boundaries; production queue callers use the snapshot form. Tests deliberately deliver newer then older commits, an equal-version different token, and an old selection after a newer pause. The prior priority probe found zero mismatches in 200 trials; that was an unconfirmed residual, not an observed race. Deterministic admission assertions now cover the source ordering contract. `PlaybackCommand.selectAt(media:occurrence:position:)` carries a restored position. The optional `onSelection` callback reserves the exact playback generation before provider/engine awaits. The boundary rejects an obsolete reservation; Domain publishes that candidate only if transport/context/seek revisions still match. Binding therefore exists before an engine can complete. No media eligibility checks are bypassed.

`QueueCommand.resume` preserves the current occurrence and checkpoint position, rotates/binds its token and routes `selectAt` through the shared Domain owner. Domain holds a pending seek until preparation and seeks before starting audio. Explicit `select(id)` remains a fresh start at zero. Restoring a queue alone never invokes either playback path.

Compose the single owner in this order: create `QueuePlaybackLifecycle`, pass it to `PlaybackCommands`, create `PlaybackQueueBoundary`, create `QueueCommands`, then attach queue/boundary/request to the lifecycle before playback. Domain engine events go through `PlaybackCommands.receive`; its lifecycle sink delivers exact scoped ends and checkpoints to the queue. Domain also owns same-generation wake and public Play; these are not new queue selections. Their accepted play acknowledgement publishes a lifecycle checkpoint. Same-context passive pause/play records intent and position without rotating the bound token; a genuine route-generation pause invalidates it. EOS rechecks the actual Domain context and intent before applying the token, including an end arriving before an awaited wake acknowledgement. A paused observation cannot authorize advancement. Item/account/route changes and explicit queue cancellation still invalidate old completions; a subsequent fresh selection/resume must go through QueueCommands. Tests use real Domain sleep→wake and pause→play, the actual forwarding boundary and actual sink, with synthetic engine/resolver only. The queue serializes them with local writes. Account lifecycle detachment pauses/checkpoints through the owner and clears the binding. Normal window closure retains this composition. Route/account/quit owners continue to use the same command/lifecycle boundaries. Actual AVFoundation, window and device composition remains W06 and the relevant later nodes; T05 exercises these seams through real Domain commands and synthetic held resolver/engine implementations only.

## Persistence, bounds, cursor and history

The SQLite adapter uses W03's existing FULL-sync transaction for header, ordered occurrences, seed, position, repeat/autoplay and a versioned `local-queue-v2:` continuation envelope. The envelope contains source context/page cursor, local consumption cursor, active immutable IDs, active recommendation provenance and bounded recent local listening. It is queue-owned state, never a provider token passed verbatim upstream. Legacy plain continuations and v1 dictionary envelopes remain readable. V2 encodes each distinct recommendation source/cursor once, with occurrence-ID groups referring to that source. The in-memory occurrence-to-provenance map remains intact and is reconstructed exactly on read, including nil versus empty cursors. Duplicate or unknown occurrence references fail validation. The adapter normalizes older near-limit checkpoints on load before they can keep growing.

`contextCursor` is the first unconsumed original order among the loaded source context; if none remain, it is one past the last retained source order. Removed originals are resolved locally. It is independent of the playback permutation and never jumps over an unplayed original. `metadata.cursor` is the separate provider source-page cursor. Pagination must use that provider cursor, never infer pages from the local consumption cursor. Consumption flags carry the noncontiguous played set through shuffle and restart.

Consumed recommendation, ad and replaced-context rows retain a tail of at most 100 occurrences. Their recommendation provenance and immutable-ID metadata expire on consumption. A consumed non-ad immutable item becomes non-repeatable history before its immutable marker expires. Consumed ads retain their ad segment and consumed flag until eviction; evicted entries cannot be selected, undone or reconstructed by Repeat all. Only a verified source boundary can install a new service occurrence. Loaded deliberate source context stays available for Repeat all/unshuffle within the 100,000-occurrence queue cap. This separates a bounded recent tail from the deliberate context whose order must be reversible.

Recent local listening is independently limited to 100 actual-event records, with pause and clear controls. Advancing a queue never fabricates a play or changes remote history. Full durable history retention remains with the history feature/store contract. Undo retains 20 local edit snapshots, is process-local, persists the resulting edit, and preserves later position, history and advanced preference changes. Transport/context/service transitions clear undo so it cannot resurrect consumed source entries. Clear/remove/move/undo require no network transport.

Raw envelope inputs are validated before base64 encoding so credentials and signed URLs cannot be disguised. Individual metadata strings are limited to 4,096 UTF-8 bytes and the existing envelope limit is 65,536 bytes. Oversized active batches fail atomically, without truncation. Consumed cursor/provenance growth no longer makes a long sequential session permanently exceed that limit. Active recommendation provenance is capped at 1,000 references; the total encoded envelope is independently capped at 65,536 bytes. Oversized distinct-source batches fail atomically and can be reduced or cleared. Shared-cursor batches are not rejected from repeated cursor copies: real-SQLite tests cover 50×1,000-byte and 12×4,096-byte cursors, as well as 1,000 occurrences sharing a 4,096-byte cursor. These are application representation bounds and synthetic input sizes, not measured provider limits.

## Speculative native preparation and listening intervals

PlaybackSession retains at most one next-item task/candidate. The current-item prepared hook only schedules that task; it does not await reservation, resolver, provider admission or next-track normalization. Cancellation retains the task handle until cooperative work finishes, so an unresponsive provider cannot accumulate replacement tasks. Selection, queue edits, pause, route/account changes and Quit cancel it. Native installation still requires the durable reservation and exact context, token, occurrence and reservation checks. A late candidate may require ordinary buffering; asynchronous preparation is not a guarantee of gapless readiness. Speculative errors remain separate from current playback failures, with the existing bounded retry delay.

Local history records occurrence-scoped playback intervals. Actual playing acknowledgement opens an interval; pause, buffering, end and manual current changes close it. Resume opens a fresh interval when playback starts, excluding the paused/preparing span. Manual skip records only listening already observed, without crediting skipped entries. Native adoption atomically records the outgoing interval with consumption, and opens the next occurrence's interval; absence of an observed outgoing interval creates no history record. Wall-clock rollback clamps an interval's end to its start. These timestamps describe injected or observed transport events; they are not acoustic measurements.

## Native adoption commit and competing controls

A native handoff drains already-entered session controls before starting its save. From that point through queue/native/Domain/boundary publication, current-changing controls from every session command origin wait for adoption. Seek/scrub then target the committed occurrence; pause and system sleep pause it; wake retains ordinary resume policy. Next or select may deliberately skip the newly committed occurrence. Previous deliberately replays the previous occurrence as a new listening interval. Remove cannot remove the newly current occurrence and is rejected without canceling its ready pipeline. Rejected queue commands validate before scheduling cancellation. Readers receive a stable coherent pre-commit snapshot rather than waiting on the save.

Quit bypasses this barrier to stop output immediately, then waits only to persist pause against the committed occurrence. It does not prepare a new player after closure. Cold restore uses that paused queue identity. If a provider/backend independently disappears after commit, recovery uses the committed occurrence at the last known native handoff position through the normal permission-aware selection boundary; the original error is retained and propagated. A local sequence change never discards a successful durable commit.

Only a persistence exception from the validated handoff save is retryable as `QueueHandoffCommitError`. The shared production session handoff handler retains the native transition and outgoing listening interval, retries at most twice (100 ms, then 200 ms, within a 400 ms budget that stays below the ~0.68 s of already-queued output), and publishes identities once. The pump and every control wait on the adoption barrier only for that bound. If the save still fails, the handoff is abandoned deterministically: the queue's durable state (the previous item current) stays authoritative, playback pauses at the end of the previous item, the staged next item is withdrawn from the engine, nothing is credited to it, and the fault is reported in the session's `failures`. Once the adoption barrier is released the abandonment also commits the queue's own pause (intent, the position at the end of the previous item, the stale handoff cleared), so the saved queue no longer reads `intent=play` with a handoff and a plain Play after recovery does not replay the end of the previous item or credit it again; a newer control that already took ownership of the queue is left alone. Later selection or resume re-saves and fails visibly while the fault lasts. Source authorization, corruption, validation and stale-context errors are not converted into persistence retries. Quit stops these retries. Normal paused/idle service does not start them. The device-free pump seam invokes the production `serviceDecoded` path with manual output established before start. It is internal test support, not another product transport.

An adopted occurrence with zero native progress has no listening interval yet. Its first progress observation opens the interval at the handoff time; immediate Next/select records no fabricated listening for it. These event timestamps remain distinct from acoustic evidence.

Timer-envelope owner resets follow the same cancel-before-reset contract as other controls. An unchanged fade factor is a no-op, so clearing an already-clear timer preserves staged next audio even in the queued window before identity adoption. Actual factor changes withdraw the owner's next reference before decoded staging is reset. Native adoption publishes its start through the Domain transaction; it does not enqueue a duplicate native started event that could outlive a subsequent same-context sleep.
