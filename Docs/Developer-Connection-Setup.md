# App-owned developer connection setup — E01

Prepared 2026-10-28. The original research supplied instructions only. On 2026-10-28 the owner requested browser setup, and the operator created the separate **YTMuse** project (`ytmuse-513012`) and its **YTMuse Desktop** OAuth client. The Console shows External / Testing, two owner-authorized test users, and only `openid` plus `userinfo.profile` consent scopes. Public registration and redacted Console observations are in [the registration record](../artifacts/harness/nodes/E01/registration/20261028T125003Z/registration.json). No billing or additional API enablement was performed, and unrelated projects were not modified. Actual app consent/token acceptance and Music access remain separate, unverified steps.

These are one-time operator instructions for the documented Google profile/YouTube read route, not normal-user onboarding and not a Music playback unlock. The public identifier is kept in the ignored local `.env.google.local` for development builds; no optional client secret was copied or downloaded.

The first normal consent attempt exposed an incomplete configuration: Google's token endpoint requires a client secret for this registration. The original general optional-field guidance did not establish acceptance without it. A same-client secret was subsequently supplied through BB's secure credential form and provisioned into the exact app-owned Keychain configuration record for the final signed build. No value is in this document, the build environment or committed evidence. The ignored private setup file is `.env.google-secrets.local`; consume it only through the reviewed [operator helper](../Tools/ProvisionGoogleClientSecret.md). A rebuilt ad-hoc signed executable may need exact-target reprovisioning. The successful write and synthetic invalid-code preflight do not establish real app consent/token acceptance. See [the integration receipt](../artifacts/harness/integration/E01-feedback-final-20261028/report.md).

1. Operator identifies an independently controlled app project and confirms permission to administer its OAuth registration. If none exists, parent must resolve that resource decision separately; this work does not create one or choose a connected unrelated project.
2. In **Google Auth platform → Branding**, configure app name, support email and developer contact. Supply privacy policy, homepage/terms and owned domains where required for the intended distribution/verification. In **Audience**, select External for a public consumer app (Internal only for a real organization-only deployment), keep development in Testing, and explicitly add the dedicated consenting account as a test user. Keep test-user email/account details in operator configuration, not committed evidence. [Official consent setup](https://developers.google.com/workspace/guides/configure-oauth-consent).
3. In **Data Access**, declare `openid profile`; add `https://www.googleapis.com/auth/youtube.readonly` only for actual documented channel/private read functionality. Enable **YouTube Data API v3** in that same app-owned project for those calls. No API key is needed for the bearer-authenticated `channels.list(mine=true)` proof. No write, partner, TV or speculative Music scope is needed for this phase. Broader scopes are not a remedy for missing native media access.
4. In **Clients → Create client**, select **Desktop app**, name it for this app and record its public client ID. Use the app's system-browser authorization-code PKCE flow and loopback `http://127.0.0.1:<ephemeral-port>/oauth2callback`, identical between authorization and token requests. This is not a Web application redirect registration or a TV client. Validate the real registration's acceptance during later ordinary app consent. [Desktop instructions](https://developers.google.com/identity/protocols/oauth2/native-app).
5. Record publishing/verification status and any verification requirement for chosen scopes. Testing does not constitute production approval. An External Testing grant including YouTube scopes normally has a **7-day refresh-token lifetime**; the basic OIDC-only exception must not be generalized to YouTube reads. Handle actual expiry/revocation; do not claim perpetual refresh. [OAuth expiration rules](https://developers.google.com/identity/protocols/oauth2#expiration).

Public endpoint identifiers: issuer `https://accounts.google.com`; discovery `https://accounts.google.com/.well-known/openid-configuration`; authorization `https://accounts.google.com/o/oauth2/v2/auth`; token `https://oauth2.googleapis.com/token`; revocation `https://oauth2.googleapis.com/revoke`. Validate OIDC signature/JWKS, issuer, audience, expiry and nonce; bind state/PKCE/redirect/account generation. An API bearer token and OIDC ID token have different audiences/purposes.

Without consent, documentation and code can establish endpoint shapes, registration requirements and trust boundaries. They cannot establish actual granted scope, account/channel selection, Music membership, region/entitlements, Desktop bearer acceptance by Music, renewal behavior or a permitted native variant. No secure input needs to be supplied to this research worker. The parent can later provision the app's public configuration; normal app/browser consent supplies runtime secrets directly. Full Music playback additionally needs the source access decision described in [route readiness](Service-Route-Readiness.md).
