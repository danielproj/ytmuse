## Implemented Music session mechanism — E01 lane M2

Code: `Packages/NativeMusic/Sources/AccountSession/WebSession/` (cookie session, signer, WebKit sign-in, coordinator) and `Packages/NativeMusic/Sources/YouTubeMusicAdapter/SignedMusic.swift` (signed client). No live run has happened yet; the operator's live sign-in is the evidence. It proves Music sign-in and private reads only — not playback, Premium, ads, offline or Cast.

- **Sign-in.** A native glass sheet hosts a `WKWebView` that loads `accounts.google.com/ServiceLogin?service=youtube` continuing through YouTube's sign-in handler to `music.youtube.com`.
  - **Navigation.** Main-frame navigation is limited to the sign-in path: `accounts.google.com` and the country `accounts.google.*` hosts, `accounts.youtube.com`, `www.youtube.com`, `music.youtube.com`, `consent.youtube.com` and `consent.google.com`. `gstatic.com`, `googleusercontent.com`, `googleapis.com` and other Google/YouTube hosts are allowed for subframes only; `about:blank` and `about:srcdoc` too.
  - **Completion.** Both conditions must hold: navigation is on `music.youtube.com`, and the store holds a live `SAPISID`/`__Secure-3PAPISID` plus `SID`/`__Secure-3PSID` for `.youtube.com`. A cookie change that lands while a check is in flight triggers one more check.
  - **Other endings.** Cancel, close, Escape, a network failure, web-content termination and a 15-minute timeout end the attempt and show a visible state.
- **Web data stores are transient (operator decision, rework 1).** Every sign-in attempt, fresh or reconnect, gets a **new** `WKWebsiteDataStore(forIdentifier:)` identifier, unrelated to the account UUID. This means stale or foreign cookies can never satisfy a later attempt.
  - **Ledger.** The attempt ID is written to an owner-only ledger (`~/Library/Application Support/local.native-music.development/web-sign-in-attempts.json`, 0600 in a 0700 directory; UUIDs only) **before** the store is constructed.
  - **Teardown.** When the attempt ends — install, failure, cancel, timeout or a different-account refusal — the following happens in order:
    1. The page is stopped.
    2. All website data and every cookie in that store are wiped while the store object is still alive.
    3. The web view is released.
    4. The coordinator wipes again, then removes the store directory in the background. It retries with bounded backoff (about 90 s in total), continuing after the sheet has closed. On the first live run the store was still in use for the ~2 s the earlier code waited.
    5. The ledger entry is cleared only after directory removal is confirmed.

    Unconfirmed entries are retried before the next sign-in, in a bounded one-second attempt at quit that never blocks termination, and at the next launch.
  - **What persists.** After installation no WebKit store holds the Google web session (including the `.google.com` SID family). The account's Keychain record is the only durable copy of the session.
  - **Sign-out and removal** make no WebKit call.
  - **Reconciliation.** Entries left by an interrupted run are removed after the first window is up, on the main actor. Removal first initialises WebKit (`WKWebsiteDataStore.default()`), because a cold `remove(forIdentifier:)` or store enumeration crashed the app at launch. The app never enumerates stores.
  - **Accepted risk.** The website's own periodic cookie refresh (`RotateCookies`/PSIDTS) does not run outside the sign-in page. Rotation arrives only through `Set-Cookie` on Music responses, so sessions may need signing in again sooner. This will be measured in the live run and over the following days, and revisited with the user if needed.
- **SEC04.** The password is typed into Google's own page. The app registers no script message handler, never calls `evaluateJavaScript`, and never reads, injects into or autofills Google's form. It never sees or stores the password, and it reads no other app's session or browser database.
- **Allowances.** Both were decided by observation on the first live sign-in (2026-10-28, `artifacts/harness/nodes/E01/web-session-live/20261028-first-live-signin/record.json`).
  - **(a) User agent — not needed, off.** Google's page loaded with the default user agent. `defaults write local.native-music.development YTMuseSignInSafariApplicationName -bool YES` appends Safari's application name if Google ever rejects the engine.
  - **(b) Passkey suppression — needed, ON by default.** Google offered a passkey challenge that cannot complete in an app web view, because Apple reserves in-web-view passkeys for browser apps. A document-start script now runs only on `accounts.google.com` and the country `accounts.google.*` hosts, and only removes the WebAuthn capability (Kaset ADR-0033), so Google offers its other methods. `defaults write local.native-music.development YTMuseSignInSuppressPasskeys -bool NO` disables it.
  - **Real passkey support** is a separate future lane, requested by the account holder.
- **Session store.** Only allowlisted `.youtube.com` cookies are copied, into one exact Keychain record through `SessionVault`, bound to the local account UUID and generation. That set is the SAPISID and SID families, the PSIDTS/PSIDCC variants, `LOGIN_INFO`, `PREF`, consent cookies and visitor cookies. The record carries provenance, its capture time and its rotation time from an injected wall clock. Cookie values never reach SQLite, UserDefaults, logs, errors or UI models; every description is redacted. Allowlisted `Set-Cookie` rotation on Music responses is written back in place (`SessionVault.replace`), and only while the same owner generation is current.
- **Signed client.** `POST https://music.youtube.com/youtubei/v1/{account/account_menu,browse}?prettyPrint=false` with the `WEB_REMIX` client version from the existing public bootstrap. Headers: `Cookie`, `Authorization: SAPISIDHASH <ts>_<sha1(ts SAPISID origin)>`, `Origin`/`X-Origin: https://music.youtube.com`, `X-Goog-AuthUser: 0`. The transport uses the existing direct configuration: ephemeral, no shared cookie jar, credential store or cache, and redirects refused. Response caps are 1 MB for the menu and 4 MB for browse, with bounded JSON. The exact path/query allowlist is checked before any I/O. An avatar is fetched credential-free from three exact image hosts, capped at 512 KB and 1024 px. Only explicit signals — 401, 403 or `loggedOut` — mean "session expired — sign in again", and local data is kept.
  - A menu whose header is missing or unknown is "unrecognised"; it never expires the identity.
  - The stable identity is the menu's single distinct `UC…` channel ID. None, or more than one, is "unrecognised". The handle is display-only.
  - A local Keychain read or write fault is a distinct local failure that never rewrites the account state.
  - An unparseable or unknown shape is "unrecognised", never an empty library.
- **Not approved, not implemented.** A hidden or embedded web player, player calls, media fetches, player JavaScript, signature deciphering and attestation tokens.

## Browser-to-Music handoff: what remains missing

Standard OAuth transfers a one-use authorization code to this app; it does not export the browser's Music cookies. ASWebAuthenticationSession/system-browser navigation is not an API for extracting another browser's session. W04 already supplies a one-use lifecycle challenge and Keychain installation boundary; it still needs verified service identity and authorization inputs.

If Music requires a separate credential, the source/access owner must identify an authorized exchange endpoint and grant binding (Desktop client/audience, subject/channel, permitted operations and renewal/revoke). A safe candidate contract would exchange a short-lived source-issued one-use code bound to state/PKCE and the initiating account generation over direct TLS. YTMuse would validate the returned Music identity and store only the protected credential reference. This is a **required contract proposal**, not an assertion that Google provides such an endpoint. There is currently no verified safe alternative transfer. Cookie/header copying, browser database access, password capture, another app's Keychain, WebView session interception and TV credential substitution are not selected solutions.

For channels, map validated Google `sub` to a user-confirmed channel and the Music session's own identity. A channel selector from one API cannot prove Brand Account/Music identity selection on another. Bind account, channel, region and generation to all requests, credential references, capability checks, cursors and results. Never share an unscoped cookie jar or default authorization header.

## Source obligations and retention

The rechecked [YouTube API developer policies](https://developers.google.com/youtube/terms/developer-policies) govern public API use; the [service terms](https://www.youtube.com/static?template=terms) govern the service separately. Their documented constraints include prior approval for storing audiovisual copies, restrictions on offline availability, ad interference, audio/video separation, background players and alternate access. Therefore this dossier cannot infer authorization for the full native product from the standard Data API. This is an engineering access dependency, not a declaration that an account is service-restricted or that no authorized arrangement could exist. Obtain a source-specific grant and reconcile its scope with the product before implementing native media/retention.

For a selected Data API route, record consent/privacy policy, independent status/required attribution and links to YouTube terms, Google privacy and account permission controls. Request scopes only for actual functions; deliberate writes require user consent. Track quota and audit/verification status; do not distribute unrelated keys or split projects to evade quota.

Retention must distinguish API metadata, artwork, local-only state, credential/session material and source audiovisual media. General authorized and non-authorized API data categories in III.E.4 require refresh or deletion within 30 days, subject to the policy's specific exceptions and periodic reauthorization obligations; do not reduce every category to one invented blanket rule. App-requested consent revocation and deletion requests have seven-calendar-day deletion obligations in the documented cases; revocation through Google permission settings has its own periodic validation/deletion rules, including the documented 30-day limit. Implement immediate local revocation/removal where possible and retain policy-specific maximum deadlines. Source cache headers and shorter rights expiry can shorten retention. The product's 5/15-minute/24-hour freshness defaults are not retention permission.

Record `policySource`, `policyVersionOrCaptureHash`, `fetchedAt`, `refreshBy`, `deleteBy`, `subject/channel`, `consentReference`, `cacheDirective` and `grantReference` per retained category. Do not persist signed media URLs as ordinary metadata. Existing W04 sign-out/removal semantics must be rechecked against the selected source's mandatory API-data deletion rules; retaining inaccessible authorized metadata indefinitely is not established as compliant. Local queue/preferences explicitly created by the user need separate provenance from API-derived private data. Backups, artwork, FTS, outbox and extension snapshots must obey the same deletion scope.
