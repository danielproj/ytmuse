# App Intents, entities and audio schemas (W24)

This is the contract for MAC03, MAC04, ARCH03 and ARCH09 as the app ships them. The code is `Packages/NativeMusic/Sources/SystemIntegration/Intents/` (intents, entities, schemas, hub), `Sources/AppShell/Intents/AppIntentChannel.swift` (the app's side) and `App/Sources/NativeMusicShortcuts.swift` (the app's shortcuts); the phrases are `Resources/AppShortcuts.xcstrings`. The tests are `Tests/PlaybackTests/Intents/` (`scripts/test.sh --suite T24`); `scripts/check-intents.py` reads the built bundle.

## Intents run in the app process

There is **no intent extension**. An App Intent runs in the app's own process, so it can use the one playback owner without a second player, a second network session or a copy of any credential (ARCH09 as W24's addendum interprets it: the "minimal command channel" is `IntentCommandChannel`, an in-process protocol; the intents themselves claim no App Group and embed no `.appex`; since W25 a bundle SIGNED with a team holds exactly ONE extension, the widget, and exactly ONE Team-ID-prefixed App Group for it, while every ad-hoc or unsigned build (all worktree and test builds) holds none of either; `check-intents.py` fails on a second extension, another extension point, another or an additional group, an extension with any entitlement beyond the sandbox and that group, or any extension or group in an ad-hoc build: see `Docs/Widgets-Spotlight.md`). `Extensions/Sources/NativeMusicIntentSupport` stays an empty scaffold that registers nothing.

```
Siri / Shortcuts  ->  App Intent (SystemIntegration)  ->  IntentHub.shared  ->  AppIntentChannel (AppShell)
                                                                                    |-> PlaybackModel.remote(_:)      (media keys' entry: capabilities, ad rules, Play here)
                                                                                    |-> PlaybackModel.playMusic       (search / library Play, permit captured at the request)
                                                                                    |-> remote(.setLike/.setSave)     -> ShellCoordinator -> W12 ledger
                                                                                    |-> ShellCoordinator.showQueue / showMainWindow / showSearch
                                                                                    '-> nativeEnableTimer + setTimer  (the transport menu's sleep timer)
```

An intent file imports `AppIntents`, `MediaIntents`, `Foundation` and nothing else of the app. `IntentDefinitionTests` sweeps them for imports of Playback, AccountSession, Persistence, WebKit, AVFoundation, Security, Downloads, `URLSession`, `FileManager`, `UserDefaults` and Keychain calls.

### Cold launch (T24.3)

The app installs its channel while it builds its scenes (`LocalAccountBootstrap.installIntents()`, from `NativeMusicScenes.init`). An intent that arrives first waits (default 20 s, `IntentHub.startupTimeout`) for the channel, then for `awaitReady()`, which waits for the account restore (`LocalAccountBootstrap.load()`, idempotent), and otherwise answers "YTMuse is still starting" and does nothing. The restored session is the W21 one: paused, nothing loaded. Only an explicit play request plays it: `ResumePlaybackIntent` (and a media-key-style Play) sends the same `remote(.play)` the Play button sends, which loads the saved playlist and item and moves to the saved position. Next, Previous, Seek, Like and Save on a restored item are refused with the window's own sentence ("This item is waiting where you left it. Press Play first."). A login launch stays menu-bar only (W21).

### Signed out, and what each intent really needs

An intent is gated by the capability it uses, exactly as the window or the media key is. The live YouTube Music session is required only by what starts YouTube Music or carries an entity of an account: **Play audio**, **Play from Search**, and Like / Save **of a given entity**. Everything else meets the same gate with or without a session: Pause, Resume, Toggle, Next, Previous and Seek follow `remoteCapabilities()` (so they work on owned and local media with nobody signed in, as the media keys do); Show Player and Show Queue always work; the sleep timer works for the native engine with no account; **Search** runs the window's own search, which is anonymous when signed out (W10), and Like / Save of the playing song follow the library gate (owned media has none, a signed-out song's page has no control). `IntentTransportTests` asserts parity with the media key's capability set in each signed-out state, with and without an advertisement.

### Gates, exactly as for a click

| Intent (command) | Goes through | Gate that can refuse it |
| --- | --- | --- |
| Play or Resume (`resume`), Play or Pause (`toggle`) | `remote(.play / .toggle)` -> `WebMusicPlayer.resume / playPause`, native `nativeStart` | nothing loaded -> "Nothing is playing"; **Play here** after a route loss: the prompt is raised in the window (which comes forward), the intent answers "Confirm Play here in YTMuse", nothing sounds before the answer |
| Pause (`pause`) | `remote(.pause)` | nothing loaded; allowed during an advertisement |
| Next, Previous | `remote(.next / .previous)` | advertisement ("cannot be skipped"), restored item, no queue, Play here |
| Seek (`seek`) | `remote(.seek)` (clamped by the player's admission) | advertisement, restored item, not seekable; a negative, infinite or NaN position is refused first |
| Play audio (schema `audio.playAudio`: song, album, artist, playlist, mix) and Play from Search (`MediaIntents.AudioSearch`) | `playMusic(playlistID:title:videoID:params:request:)` with the permit captured at the request | account and generation fence (`staleContext` -> "belongs to a different account or an earlier session"), signed out / expired, Play here (held start keeps its permit), nothing to start ("YouTube Music gave this item nothing to play") |
| Like This Song, Save This Song, schema `audio.updateAudioAffinity`, `audio.addToLibrary` | `remote(.setLike / .setDislike / .setSave)` -> `RemoteLibraryControlling` -> `LibraryControlPress` -> **W12 ledger** | advertisement (refused before the library is even asked), owned or local media, the song's page not read (no control), a state that already holds presses nothing; only the song that is playing can be liked or saved |
| Search (`search`; adopts `AppSchema.system.searchInApp`) | `ShellCoordinator.performSearch` -> `SearchRequestInbox` -> the first visible, frontmost window opens Search, types the words and presses Return; the intent waits for **its own** request to be performed | empty or oversize (> 512 bytes) query refused; if no window did it within 8 s the request is withdrawn, and if a newer Search replaced it the older intent is told at once; either way it says its words were not searched |
| Show Player, Show Queue | `showMainWindow`, `showQueue` | none; the queue panel says YouTube Music manages the upcoming items |
| Set Sleep Timer | native engine: `nativeEnableTimer { setTimer }`; YouTube Music: `setMusicSleepTimer` (P17-WEB) | both engines, as in the transport menus; YouTube Music fades the page's volume over 5 s at expiry (never during an advertisement) and pauses, End of item pauses at the boundary the page reports; refused in plain words for a live stream's End of item, a length outside 1 s-24 h, and nothing playing; Play here / timer note gate the native engine |

"Like" and "Save" from an intent are user-initiated by definition (a person invoked it), and still go through the ledger's one-operation rule and its account scope. Their sentence says "Asked YouTube Music to like this song"; the ledger shows done only when the service confirms.

What an intent refuses **by name** instead of ignoring: a queue position (`next` / `tail`), `shuffle`, `repeat` (YouTube Music manages the upcoming items; the app has no shuffle or repeat control for the hidden player, and a shuffle needs parameters only a page can publish).

## Entities are scoped to the account, and work in flight to the session (T24.2, DATA03)

Operator decision (W24 rework 1): a saved Shortcut must keep working across a relaunch and across signing in to the SAME account again, and must be refused for any other account. So an identifier is `ytm1:<account>:<kind>:<payload>`: the stable `AccountContext.accountID`, the kind, and the title, subtitle and ids the catalog row published (`videoID`, `playlistID`, `browseID`, `params`), never a credential. **No per-launch counter is in it** (`AccountLifecycle`'s generation restarts at 0 in every process and moves on every sign-in, so it cannot identify anything across launches).

- The channel admits an entity only when its account equals the live session's account (`AppPlaybackAuthority.activeScope()`, read at the call). Another account or a malformed identifier: `staleIdentity`, one sentence that names neither account. Signed out: `signedOut`. A query refuses the **whole request** if any identifier is foreign.
- **Work in flight (DATA03) rests on three things, none of them a shared timer**: the account check at the moment each command runs (against the live session), the start permit captured at the request (`authority.requestOwnedStart()`, which the authority rejects across an account barrier), and, for a spoken name, that invocation's own recheck that the session it started in is still the live one after it read the library. Nothing is shared between intents, so concurrent intents cannot widen, shorten or overwrite each other's fence (`twoConcurrentIntentsAreEachHeldToTheAccountTheyRunUnderAndNeitherDisturbsTheOther`). An earlier hub-wide 120 s "resolution stamp" was removed: it was arbitrary, overwritten by concurrent intents, and added nothing the account check and the permit do not.
- Queries (`entities(matching:)`, suggestions) read **loaded** library rows (`LibraryCollectionModel.entries`, never triggering a read) and the radio seeds the person has met (`RadioSeedBook`). They make no request the window would not make. Recent search results are not a source: each window owns its `SearchModel`.
- **Duplicate titles are never reduced to one.** `IntentResolver.resolve` returns `.many` for equally good matches. The entity queries return all of them (the system asks the person). For a spoken name (`PlayMediaSearchIntent`) the intent asks the person with the SDK's `requestChoice(between:)` (distinct lines: title, subtitle, kind; at most five) and plays the one picked; if the interaction cannot be had or is cancelled it reports the ambiguity and plays nothing.
- **One item is one candidate**: items are keyed on identity (kind and video, playlist or page id), not on the context they were listed in, so a song in both Songs and Liked songs is one choice.
- A **mix** is only a radio the service itself presented as one (a `RadioSeed` from a "Start mix" action). An `RD`-prefixed playlist in the library is a playlist.
- An **artist** is playable only through the radio action its row published. Private service media has no catalog target and is not offered.

## What the SDK declares (macOS 27.2 SDK, checked against the interface files and the SDK's own validator)

Read from `AppIntents.swiftinterface` and, for the required members, from the diagnostics of `appintentsmetadataprocessor` itself (a schema's shape is not in any readable file; the processor lists each missing member).

- **`AppSchema.audio`** (`anyAppleOS 27.0`) declares intents `addToLibrary`, `addToPlaylist`, `createStation`, `playAudio`, `recognizeAudio`, `updateAudioAffinity`, `warmupAudioQueue`; entities `album`, `algorithmicRadioStation`, `ambientSound`, `artist`, `audiobook`, `classicalMusicRecording`, `liveRadioStation`, `newsBrief`, `newsProvider`, `playlist`, `podcastCollection`, `podcastEpisode`, `podcastShow`, `radioShow`, `radioShowEpisode`, `song`, `songCollection`, `warmupAudioQueueResult`; enums `appViewIdentifier`, `affinityState`, `activity`, `invocationSource`, `playbackAttributes`, `queueInsertionLocation`.
- **Adopted** (all validated by the processor in the built app): intents `playAudio`, `addToLibrary`, `updateAudioAffinity`; entities `song`, `album`, `artist`, `playlist`, `algorithmicRadioStation` (the mix), `warmupAudioQueueResult` (a `TransientAppEntity`, required as an optional parameter of `playAudio`); enums `queueInsertionLocation` (`next`, `tail`), `affinityState` (`like`, `dislike`, `unset`), `playbackAttributes` (`shuffle`, `repeat`). `audioEntity` and `target` must be a `@UnionValue` of the entity kinds (here `AudioTarget`: song, album, artist, playlist, mix), and each entity needs an `EntityStringQuery`.
  - Required members that the app has no honest value for are optional or empty, never invented: a song's `albumTitle`, `composerName`, `internationalStandardRecordingCode`, `album` are nil; `artists` and `composers` are empty; a playlist's `createdByMe` and `curatedForMe` are nil.
- **Not adopted**: `warmupAudioQueue` (nothing may load or play before an explicit play, so there is nothing to warm), `recognizeAudio`, `createStation`, `addToPlaylist` (playlist editing from an intent is not part of MAC03), the podcast, radio-show, audiobook, ambient, news and classical entities (no source in the app's caches).
- **`AppSchema.system.searchInApp`** (`anyAppleOS 27.0`, `SystemSearchInAppIntent`; also `.system.open`). `SearchInAppIntent` adopts it (conforms to `ShowInAppSearchResultsIntent`: a `StringSearchCriteria` `criteria` and `searchScopes`; the processor validates it in the built bundle). It replaces the deprecated `.system.search` / per-domain `search`. `.system.open` is not adopted: the app has no "open this entity" intent in MAC03.
- **Media search**: `MediaIntents.AudioSearch` (`criteria`: `unspecified`, `searchQuery(String)`, `url([URL])`) is a system intent value (`com.apple.siri.MediaIntents.AudioSearch` in the generated metadata). `PlayMediaSearchIntent` takes it as its parameter; a query plays only an unambiguous playable match, a URL is refused (links open native destinations in W26, never a command from here). Whether Siri routes "Play X in YTMuse" to it is a live observation.
- `NowPlaying.MediaContentRepresentable.appEntityIdentifiers` (`_NowPlaying_AppIntents`) exists and would tie the now-playing item to an entity; it is **not** used (a live observation decides whether "Like this song" binds through it), so "Like this song" is the plain `LikeCurrentSongIntent` with an App Shortcut phrase.

## Donation

Nothing in this node donates an intent or interaction to the system, in production or in a test, and nothing refreshes the App Shortcuts parameters or relevant intents. Three layers keep it so, because each alone can be renamed around:

1. **Text, name-agnostic** (`IntentDonationGuardTests`): every `donate(` in Swift is a violation unless its line is one of the app's own (`func donate(`, `donations.donate(`, `hub.donate(.command...)`, the hub's own `donate(command, ...)`), so `action.donate()`, `PausePlaybackIntent().donate()`, `x.donate(result:)` and a bare `donate()` are flagged whatever the variable is called. Plus rules for `callAsFunction`, `Intent(...)()`, an intent variable called as a function, `(donate:`, `IntentDonationManager`, `updateAppShortcutParameters`, `RelevantIntentManager` / `RelevantIntent` / `RelevantContext`, SiriKit, activity predictions, `shortcuts://`, `ShortcutsLink`, the `shortcuts run|view|list|sign` command, and `defaults write` to Siri or Shortcuts preferences. The sweep covers every Swift source, test target, UI test, the app and the extension scaffold, and every script-like file under `scripts/`, `Tools/`, `Fixtures/`, `Tests/`, `App/` and `Extensions/`. Each rule is proven on a planted line and checked not to flag the legitimate lines.
2. **Symbols** (`scripts/check-intent-donations.py`): reads the undefined symbols of every object file and binary the build produced (package modules and all test targets, the Xcode intermediates, the app and its debug dylib) and fails on a reference into AppIntents to `donate`, `callAsFunction(donate:)`, `IntentDonationIdentifier`, `IntentDonationManager` or `RelevantIntentManager`. This catches what text cannot, for example `let p = PausePlaybackIntent(); try await p()`. Its `--self-test` compiles `action.donate()`, `PausePlaybackIntent()()` and `p()` (plus `donate(result:)`, the relevant-intent manager and the donation manager) and requires each to be flagged and a clean file to pass. `scripts/test.sh --suite T24` runs it on the real build output.
3. **Behaviour**: `IntentHub.donations` is an injected `IntentDonationSink`, default `DiscardingDonationSink`; the only gate is `IntentHub.donate(_:origin:scope:outcome:)`, which refuses everything but a *successful action in the app's own UI* and records only the command's stable name and the scope. Production does not install a sink.

## Compile, Shortcuts and Siri are three claims

`scripts/check-intents.py --app <bundle>` prints them separately:

- **compile**: the built app carries generated metadata (`Contents/Resources/Metadata.appintents/extract.actionsdata`) for exactly the intents, entities, queries and schemas the sources declare, the shortcuts' phrases are in `en.lproj/AppShortcuts.strings`, an ad-hoc build embeds no extension and claims no App Group (a signed one: exactly the widget and the one team-prefixed group; W25's narrowing of the old "none"), and the widget button intent `WidgetTransportIntent` is present as a non-discoverable audio-starting system intent. This is what the build can prove.
- **shortcuts**: *declared*. That the Shortcuts app on a Mac lists the actions and tiles is not observed by any build or test.
- **siri**: *not observed*. Recognition of a phrase in any language is W41's live observation. "Play my Supermix in YTMuse" and "Like this song in YTMuse" are not proven by anything here. Siri language availability follows the OS and is not promised for every UI language; the shipped phrases are English (`Resources/AppShortcuts.xcstrings`), each naming the app once.

## Live observations (end-of-project list, never counted as passes)

LaunchServices registration: Xcode registers every Debug build (`lsregister`) as part of `scripts/build-debug.sh` / `scripts/test.sh --suite T24`. With App Shortcuts in the bundle, the system's Shortcuts, Spotlight or Siri indexes may list or launch a worktree Debug build under the shared bundle id. Debug builds are isolated by default (no real stores), so this is not a data risk, but it is the one place a test run could touch the system's Shortcuts state; whether it does is a live observation, not asserted. Shortcuts listing the actions and tiles; each phrase spoken to Siri in each supported language; "Play my Supermix in YTMuse" and "Like this song in YTMuse"; whether Siri routes a spoken name to `audio.playAudio` / `PlayMediaSearchIntent` and what it does with the `warmupAudioQueueResult`, `queueLocation` and `playbackAttributes` parameters this app refuses; a cold launch by an intent: whether the system starts the app in the background (no window, no activation), whether a window opens, how long until the channel is ready, and that nothing plays unless the intent was a play request; the Play here prompt raised from an intent with the app in the background; Like / Save from Shortcuts against a real song; the entity pickers (suggested entities from the loaded library) in the Shortcuts editor; duplicate-title disambiguation shown by the system; an old Shortcut saved under another account or an earlier session refused with the sentence; AirPods / HomePod invocations.
