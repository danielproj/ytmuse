# Native Google candidate authorization

E01 stage-auth implements the official Google identity flow. It establishes a Google subject only. The default Music bridge returns no proof; no Music account/channel, entitlement, native media, source events/ads, offline or Cast access is inferred. See the source-route lane's `Service-Route-Readiness.md` and `Developer-Connection-Setup.md` in the operator checkout for the separately missing integration resource. Those documents are owned by that lane.

The app loads the public identifier from the `YTMuseGoogleDesktopClientID` Info.plist key, expanded from the **developer build setting** `YTMUSE_GOOGLE_DESKTOP_CLIENT_ID`. Example invocation format: `Scripts/build.sh YTMUSE_GOOGLE_DESKTOP_CLIENT_ID=<app-owned-Desktop-client-ID>`; the placeholder is not usable configuration. Absent/empty/unexpanded configuration keeps authorization disabled. Invalid nonempty configuration fails rather than silently enabling it. No ID is provided or manufactured here. The production candidate requests only `openid profile` plus offline access. Registration, ownership, consent audience/test users and real loopback acceptance remain operator-controlled and untested.

Operator setup on 2026-10-28 subsequently created the app-owned YTMuse Desktop registration in project `ytmuse-513012`; see [the public registration record](../artifacts/harness/nodes/E01/registration/20261028T125003Z/registration.json). The ignored `.env.google.local` holds its public build setting only. The configured Release build succeeded and its expanded Info.plist identifier was verified. Console registration and test-user eligibility are now observed; actual app consent, callback/token acceptance, refresh/revocation and Music access remain unverified. No client secret was copied or downloaded.

When configured, the native account/welcome surface offers **Authorize Google identity**, an explicit cancellation action, and distinct status text. A successful candidate leaves the Music roster empty and says Music session/playback access is unverified. Google refresh/disconnect actions appear only for a retained live candidate; stored credentials from a prior app process can be removed. Existing Music reconnect controls are disabled in this composition because no source verifier is available. Normal account holders never create developer projects as onboarding. No browser is opened on launch, refresh, expiry or by these tests.

`GoogleConnectionCoordinator` uses one `NativeOAuthLoopback` per attempt, routes its bounded in-memory callbacks into DesktopOAuthFlow, and checks the initiating lifecycle challenge/generation before exchange publication and source handoff. The lifecycle registers it as a participant; switching, expiry, sign-out and removal invalidate the owner epoch, close listeners and invalidate the protected store permit before a late exchange/refresh can publish. Cancellation of an old attempt only cancels that exact lifecycle challenge; it cannot consume a replacement. Wrong HTTP/state callbacks cannot publish credentials. A cancelled/expired flow cannot become Connected after returning from network work.

`GoogleJWTVerifier` verifies RS256 with Security.framework using RSA keys from the exact Google discovery/JWKS endpoints. It rejects other algorithms, unknown/duplicate kid, header-supplied key locations, untrusted discovery issuer/key URLs and malformed/bounded keys. It checks signature, issuer, audience/authorized party, absolute expiry/issued/optional not-before, nonce and bounded stable subject. JWT times use an injected wall clock; cache/access/attempt lifetimes use a shared monotonic clock. Cache lifetime respects max-age/Age/no-store/no-cache with a six-hour cap, and unknown-kid fetches are paced. Expired caches never authorize a failed verification. Refresh ID tokens still require signature/issuer/audience/time and the original subject; an omitted nonce is permitted only in this refresh-specific path, and a present nonce must match the original, per OIDC Core §12.2.

Tokens are never account-view models or ordinary metadata. Authorization exchange retains pending values in memory until flow deadline/generation checks finish. Valid Google grants go into a separate exact app-owned **standard macOS Keychain** generic-password record, service `local.native-music.development.sessions.google-candidate`, account `candidate`. The record includes validated subject/client/scopes and initiating account/channel/region/generation binding. No Google record is installed through SessionVault.insert, so it cannot re-enroll a Music/offline erasure epoch. No data-protection-Keychain/distribution ACL guarantee is claimed. Sign-in stores only one Google candidate; a replacement removes the previous record and completes pending remote-revoke work before opening a new browser.

Store rotation and local invalidation execute atomically on their owning actor, with unguessable revocable permits and exact scope checks. Refresh is explicit/demand-driven, never a browser loop. Omitted refresh-token replacements preserve the existing refresh token; returned scopes cannot lose required grants, subject cannot change, actual expiry is bounded, and access lifetime starts at token receipt rather than after signature-network work. Revocation responses clear local access; transient failures remain failures. Local removal invalidates permits before Keychain read/delete and succeeds even if remote revoke fails or the stored value is unreadable. Remote revoke is bounded, best effort and tracked so local replacement does not race a still-running revoke task. A network timeout cannot prove remote revocation succeeded.

A pending Google candidate is not silently restored into a new process/lifecycle generation. Startup checks only exact-record presence, displays a stored-authorization state, and offers removal or explicit reauthorization. Removal can read that exact app-owned record solely for best-effort revoke, then deletes it. This is deliberate candidate-session policy, not a claim of Music session restoration or release-level account continuity.

The Desktop `client_secret` field is optional in the documented protocol table, but this app-owned registration's token endpoint requires it in the observed configuration. `AppOwnedGoogleClientSecret` reads a custodian-supplied value only from service `local.native-music.development.sessions.oauth-config`, account equal to this app's configured public client ID, with no authentication UI. No secret is stored in Info.plist/build arguments or printed. Runtime code/verifier/access/refresh tokens come directly from app/browser consent, never copied headers/cookies or chat. The secret provider and verifier/transport/clock/store/listener seams are injectable for ordinary tests; production has no accept-all verifier.

Only a trusted `MusicSessionVerifying` implementation can return `VerifiedMusicSession` with its own source credential, subject binding, real account/channel context, provenance reference and expiry. The coordinator validates that binding and calls the existing serialized AccountLifecycle handoff only after proof. The default bridge returns nil; no real implementation/endpoint is invented. A Google profile is deliberately insufficient input to authorize a private Music experiment or native asset admission. YouTubeMusicAdapter, StreamResolver and NativePlayer service admission are unchanged.

Primary contracts checked during implementation: [Google Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect), [OIDC Core refresh response](https://openid.net/specs/openid-connect-core-1_0.html#RefreshTokenResponse), and [Apple SecKeyVerifySignature](https://developer.apple.com/documentation/security/seckeyverifysignature(_:_:_:_:_:)). Captures and installed SecKey.h excerpts are under `artifacts/harness/nodes/E01/stage-auth/`; no third-party source was copied into production.

## Selected pre-consent corrections and Music prerequisites

The small rework after 910bf50 restricts both initial and refresh ID tokens to exactly the configured single audience (including the one-element array form); there is no trusted extra audience setting. Grant/capture/record descriptions and mirrors are redacted while protected Codable storage is unchanged. Invalid optional Google configuration, including unresolved build variables, disables authorization with configuration-specific status while local account storage continues opening. Only the known configuration error is handled there; database and Keychain failures retain their own failure paths.

The default Music bridge remains nil and Music reconnect remains disabled. L1–L3 from the independent lifecycle review are **hard prerequisites before any real bridge is enabled**: startup's default-identity switch currently detaches and revokes the Google grant; install/activation/active reconnect can revoke a backing Google grant; and Music proof expiry/provenance is not retained or enforced after the current wall-time install check. These require resolution against the actual source contract, not speculative changes in this patch. Other nonblocking F/L findings remain preserved obligations (including orphan/late refresh revocation, callback availability, cancellation/refresh messaging, store failures and cache/clock behavior). Neither Google-only review approval establishes live acceptance or Music completion.

The narrow rework-2 correction keeps stored authorization visible/removable even with missing, malformed or unresolved optional Google configuration. The shared production setup/model factory preserves cleanupRequired and reports configuration plus retained-record status together, without enabling Authorize/Refresh. Local-store tests inject a memory vault and never construct the production Keychain namespace. OAuthCodeExchange and OAuthCallback now also use opaque Swift descriptions/debug/mirrors; their operational fields and form/URL bytes are unchanged. This redaction does not hide values from a debugger or process memory. Existing L1–L3 Music-bridge prerequisites and other preserved findings are unchanged.

Rework-3 adds shared native failure/pending feedback, fixed OAuth error categories and a static browser callback receipt that directs the user back to YTMuse for the actual result. It does not report successful authorization from callback receipt. Arbitrary upstream descriptions are ignored. One exact recognized `invalid_request` description (`client_secret is missing.`) maps to secure developer-configuration guidance. Root's 20261028T125003Z official-token preflight observed that response with a synthetic invalid code and verified TLS; it establishes a requirement for this app-owned registration, not the cause of the earlier lost attempt or a requirement for all Desktop clients. Prior optional-secret documentation is preserved in rework-3/prior; the existing exact app-owned secure provider remains unchanged. Operator preparation and unverified ACL limits are in Tools/ProvisionGoogleClientSecret.md. Worker performed no real authorization or Keychain provisioning.
