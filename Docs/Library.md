# Library, history and library changes (W12)

Design notes for the Library and History screens. Library pages need the signed session, so **no anonymous capture of any library page exists**. The parser is exercised on library containers holding entries copied from the real anonymous captures (`Fixtures/W12`, mode `synthetic-from-real-renderers`, generated by `Fixtures/W12/generate.py`); the liked-songs page *is* the real playlist capture read as a collection. Everything below that depends on the signed service's actual answers is on the end-of-project live list at the bottom.

## Reading

- `MusicLibraryKind` names the nine collections (songs, liked songs, albums, artists, following, playlists, podcasts, saved episodes, uploads), the `browse` page that lists each, and the kinds of entry it may hold. `MusicHistory.browseID` is the service's history page.
- `MusicBrowseParser.parse(_:mode: .collection)` reads a library or history page with the same renderers the catalog uses. Differences from the catalog reading, all counted: repeated rows are **kept** (a song played twice is two rows; only the service's own occurrence id makes a true duplicate); control tiles ("New playlist", "Shuffle all") are *unsupported*, not members; an uploaded track (`MUSIC_VIDEO_TYPE_PRIVATELY_OWNED_TRACK`) is a song marked `isUpload`. Catalog readings are unchanged.
- `LibraryCollectionModel` keeps a collection: `entries` is the service's order and is only appended to (or replaced by a refresh). Search, sort, layout and selection are views over it and cannot change it. Paging reads every page: it stops only when the service offers no token, a token comes back unchanged, or a page replays the previous one. A page of another kind's entries is counted (`wrongKind`) and reported. Every parsed item is a row, left out, or a counted duplicate (`accountedFor`); a test asserts it on every fixture.
- States are distinct (LIB01): `loading`, `empty` (read completely), `offline`, `restricted` (needs sign-in / session ended / not offered here), `unrecognised` (never shown as empty), `failed`, `noMatches`, and `content` (with `stale` after 15 minutes — history 5 — and a `refreshFailed` reason when the saved rows are older than asked for).
- Sorting offers service order (default), title A–Z / Z–A and artist, stable for equal keys. "Recently added" is not offered: no row carries an added date, and the service's own order is the only recency the service defines.

## Changes (like, dislike, save/remove, follow/unfollow)

- Only an **explicit action on one item** sends anything. `LibraryWriteLedger` is the one command layer every surface uses (Library rows and cards, album/playlist/artist headers, song detail). It never loops, batches, polls or replays from storage; a guard test scans the sources for any other caller of the write path. Multi-selection actions are non-changing (copy links).
- What is offered comes from what the entry published for itself (`MusicItemControls`: a `likeButtonRenderer`, a library toggle, a `subscribeButtonRenderer`). **A library toggle is recognised by its icons, never by merely carrying a token** (rework 1): each side's icon names the action its own endpoint performs (`LIBRARY_ADD`/`BOOKMARK_BORDER` add; `LIBRARY_REMOVE`/`LIBRARY_SAVED`/`BOOKMARK` remove), whichever side is the default (Kaset and ytmusicapi swap the tokens when the default icon says the item is already saved); the displayed side (`isToggled`) says whether it is in the library. One add icon with one remove icon, or it is not a library toggle: the "Mark as played", "Pin to Listen again" and add-to-playlist toggles of a real signed episode row (`Fixtures/W12-kaset-real`) are ignored, an ambiguous pair, two library toggles on one entry, or an endpoint whose own `status` contradicts its icon yield no control, and song/video, album/playlist/show and artist controls are kept only on entries of those kinds. The only action membership supplies is **Unfollow in Following** (the row names the channel, `UC…` or the library's `MPLAUC…` form); no save, remove or rating is invented from membership, so the person's own playlists, Liked Music and Episodes for Later get none. Library tabs may wrap their shelf in an `itemSectionRenderer`; a collection reading looks through it.
- Optimistic with the four SYNC04 states: `pending`, `confirmed`, `failed` (rolled back, retry offered), `needsReconciliation`. **Success needs positive evidence**: a feedback response must mark every token processed; a rate/subscribe answer must carry the actions the service attaches to a change. An `error` object in an HTTP 200, or `isProcessed: false`, is a refusal; an answer that is neither is `needsReconciliation`, never done. A lost connection after the request left is also `needsReconciliation`; before it left, a plain failure.
- Operation ids are kept for the life of one action (retries reuse it). After an unknown outcome the service is read first (`check`: the artist's or playlist's own page names the follow/save state); only when that cannot tell is repeating the same state-setting request allowed. Nothing is queued offline; a change that did not leave says nothing was changed (SYNC07 — no fake pending queue).
- State is per account scope; a switch drops every pending change and discards late answers.

## History (LIB05, SYNC08)

- **YouTube Music history** is read from `FEmusic_history` and shown with the service's own day headings. YouTube's own player records it when the hidden player plays; the app never writes or imitates it.
- **Pause and clear** for the service's history are not offered: no request path exists for this app. The page says so in words (`RemoteHistoryControls`), never with an inert or local-imitation control.
- **On this Mac** is the app's own record, marked `Local only` (`SyncState.localOnly`), kept per account in a private file in the app's data directory and removed with the account. Clearing it says what it clears and changes nothing at the service.
- Plays come from real player progress: `ListeningHistoryRecorder` applies the adapter-defined `ListeningPolicy` (`YouTubeMusicListening.policy`: half the track or 30 seconds, whichever is less, of time actually heard). Buffering, pauses, advertisements, previews, seeks, rewinds and repeated end reports add nothing; an end report alone never makes a play; an occurrence records at most once; replaying after the end is a second play. The bridge cannot tell a preview from a track, so `ListeningObservation.Content.preview` is honoured by the recorder but never produced by the hidden player's reports today.
