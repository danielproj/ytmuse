# Local account lifecycle

W04 implements local identity management. It does not establish a YouTube Music session. The normal YTMuse app starts with an empty directory and exposes native account management. E01 stage-auth now supplies a separately labeled Google identity authorization flow when the app-owned public Desktop client configuration is present; it stays disabled without that configuration. Google verification leaves the Music directory unconnected until a trusted Music-session verifier supplies actual proof. See [Google auth implementation](Google-Auth-Implementation.md). Public browse is not offered before public service access is verified. The independent-client explanation and YouTube subscription ownership remain visible.

`AccountLifecycle` is the single local authority. AppShell shares one bootstrap/model across windows. Switching first reserves a newer detached generation, clears pending authentication state, and revokes Keychain access. Every registered participant then detaches: cancellation, command/playback checkpoint/stop, system ownership and SQLite access. Only after all detachments succeed can the target restore, paused, at another newer generation. Partial restoration triggers another detachment, with all hooks attempted. A concurrent lifecycle mutation returns `busy`; the caller can retry after the current operation. Authority never rolls back. Expiry preserves durable queue, navigation and unsent operations, restores local state paused, and denies credential-reference access until explicit reconnect. No browser action runs on a timer or from expiry itself.

`ScopedAccountWork` registers cancellation for search, mutation and download work. Cancellation alone is insufficient: every consumer must check its request context again after suspension. `SQLiteAccountParticipant` binds SQLite's accepted generation and exposes restored queue/navigation snapshots; queue intent is always paused. `CommandAccountParticipant` bridges the existing Domain command owners and a required `AccountSystemOwnership` sink. Future playback/system composition must register it before the SQLite participant so the previous snapshot checkpoints before storage detaches. Actual audio engines, queue execution, media-key registration and Spotlight/widgets belong to their assigned nodes; there is no fabricated active playback owner in W04.

The roster uses normalized SQLite `identities` rows and a reserved `identity:<scope>` lifecycle preference per identity. It stores labels, stable account/channel/region identifiers, state, default selection and random credential UUID references. It has no fixed account-count or aggregate-roster-size limit. Per-field metadata safety limits still apply. Profile metadata is not encrypted; private database/files are protected with 0700/0600 filesystem permissions. Sign-out retains local metadata/state while denying private access and deleting all keys for that identity. Reconnection must re-establish service authorization. Full removal never invokes a remote deletion.

The production vault uses native `SecItemAdd`, `SecItemCopyMatching` and `SecItemDelete` in the standard macOS Keychain. Exact service names include the app-owned namespace, stable local account UUID, length-framed channel and region; records use random reference UUIDs. There is no query for unrelated credentials and no credential value in SQLite, UI models, fixtures, diagnostics or extension snapshots. This development identity has no provisioning profile: a data-protection-Keychain experiment failed with `-34018` and is retained as failed evidence. No data-protection-Keychain entitlement or protection claim is made. The test suite uses separately created temporary native Keychains; the native UI host also verifies the production standard-Keychain path in an isolated app-owned namespace. Signing/access-control behavior under final distribution identity remains a release check.

Removal first tombstones the identity, then detaches access, deletes keys, and invokes every registered removal hook, even after a failure. SQLite deletes all scoped rows, lifecycle/account preferences, outbox, FTS, queue, download/artwork/index references and versioned-backup copies, then vacuums/checkpoints. `PrivateAccountFiles` deletes only the target channel's app-owned directory. Failed cleanup leaves `removalPending`, an explicit error and a Retry Removal action; it cannot activate. A retry runs idempotent cleanup again. Later download, private artwork, Spotlight, extension and system modules must register their own deletion/invalidation participant before creating private state outside this store. Files/OS indexes owned by future modules are not claimed to exist or have been tested here.

## Browser/session handoff for W31

`beginAuthentication(for:)` creates a cryptographically random 256-bit state, captures the active generation and optionally binds a reconnect identity. Only one outstanding attempt is allowed. Cancellation invalidates it. `completeAuthentication` consumes a matching callback once, checks the generation and target account/channel, stores the credential only in Keychain, and publishes only a random reference in the directory. The adapter must reconstruct the callback challenge using the actual returned state and the initiating attempt's captured generation/identity. Wrong state, wrong generation, wrong channel, cancelled and reused callbacks fail before credential installation. Credential installation rolls back its exact new Keychain record if metadata persistence fails; cleanup errors propagate.

`AccountAuthenticationAction` is the native UI injection point. W31 must supply a verified system-browser or approved authentication-session flow, validate callback URL/origin and actual state, perform PKCE where the chosen route supports it, validate service errors/identity, and safely renew/revoke the actual Music session. It must call the lifecycle handoff only after that verification and cancel the challenge on cancellation/error. A public OAuth profile/token is not presumed to authorize Music. No password, recovery-code or second-factor entry/storage field exists in the app. Actual browser Music sessions, safe transfer/renewal/revocation, free/Premium access and source restrictions remain unverified. All G01–G09 remain open.

## YouTube Music web session (E01 lane M2)

The primary sign-in is now in-app YouTube Music web sign-in (user decision, 2026-10-28; see [Service access](Service-Access.md)). Welcome offers **Sign in to YouTube Music**. The Google OAuth coordinator stays compiled, tested and registered as a lifecycle participant, but it is no longer offered in the primary UI.

`MusicSessionCoordinator` is a lifecycle participant.
- **Sign-in attempt.** Each attempt runs in a fresh, transient WebKit store whose ID is unrelated to the account. The ID is ledgered before the store exists, and the store is removed as soon as the web view is released, whatever the outcome.
- **Verification.** The coordinator then calls `account/account_menu` and requires an active-account header, taking the display name, handle and photo URL.
- **Installation.** Only after that does it install the account through `completeAuthentication`, with the Keychain record as the sole credential. The Keychain record is the only durable copy of the session.
- **Service identity.** The single `UC…` channel ID in the menu; a handle is never used as identity. The region is the Mac's region, or `ZZ` when it is unknown. Reconnect requires the same service identity and replaces the exact record. Adding an account that is already on this Mac is refused. After installation the identity becomes the active owner, restored paused at a newer generation.

The Accounts surface shows the active identity's name, handle and avatar. It also shows a read-only list of library playlists from one `FEmusic_liked_playlists` page, with titles and printed counts and no writes. "Unrecognised", "session expired" and network failures are distinct states; none of them is shown as an empty library. Proof reads, and the rotation write-back, re-check the lifecycle generation after every suspension; a switch, sign-out or removal fences them.

**Sign-out and removal.** No web store outlives its attempt, so sign-out and removal only delete the Keychain record through the existing lifecycle; they make no WebKit call.

**Quit with a sheet open.** A window with an attached sheet made AppKit refuse the quit Apple Event (-128 on the live run). The quit Apple Event and the Quit command therefore first cancel the sign-in sheet and end any attached sheet. They then call the normal terminate, so the existing shutdown checkpoint still runs. Attempt-store removal runs alongside it, bounded to one second.

**Account photo.** It is fetched credential-free from Google's numbered image hosts (`yt0`–`yt9` on `ggpht.com`/`googleusercontent.com`, and `lh3`–`lh6.googleusercontent.com`), upsized through Google's `=sNN` directive to 176 px. The first live run showed a placeholder. The likely cause, not yet confirmed live, is that the allowlist held only `yt3`/`lh3`, so a `yt4`/`lh4`–`lh6` photo was refused and the fallback glyph shown. If the live image is a letter monogram, it is Google's own default picture for an account without a custom photo.

**Interrupted attempts.** An attempt store left behind by a crash or an unconfirmed removal stays in the ledger. It is removed by a reconciliation that runs on the main actor after the first window is up, and never on the launch path.

**Expiry.** Only explicit service signals (401, 403 or `loggedOut`) move the identity to `expired`. Queue, navigation, the outbox and the Keychain record are kept until the user signs in again or signs out. An unknown menu shape or a local Keychain fault leaves the identity `connected` and shows a distinct state.

**Renewal (accepted risk).** Without the website's own cookie refresh, sessions may need signing in again sooner (see [Service access](Service-Access.md)).

**Not marked available.** Playback, Premium, ads, offline and Cast.

## Validation

`./scripts/test.sh --suite T04` requires nonempty discovery of `AccountSessionTests`, runs local lifecycle/storage/native Keychain cases, and runs the native account UI test. `NativeAccountTestHost.app` contains explicit synthetic composition under `Tests/AccountSession`; it is neither a production dependency nor embedded in `YTMuse.app`. It identifies its synthetic identities in the window, deletes its exact owned Keychain records at startup/termination, and exercises native account controls. T02/T03 retain the accepted domain/storage regressions. None of these tests is live YouTube evidence.

W04-R1 correction: removal reuses the single authoritative detached barrier for every cleanup participant, including command/system, scoped work and SQLite. It does not allocate a generation per hook. If any hook fails after SQLite has erased the profile row, the public removal tombstone is persisted again at that same barrier so a roster reload still offers retry. Existing generation high-water guards remain unchanged.

## Keychain deletions and prompts (C1)

- **Sign In Again** writes the new session record first, publishes it, then deletes the old record (macOS may ask). The old reference is written to `stale-credentials.json` (references only) before the prompt. If the deletion is refused and the roster rolls back, the new record is withdrawn. If the roster **cannot** be rolled back, the new record is kept (the roster points at it, so the session works) and the old record stays in the ledger; launch retries it with the Keychain UI off, and the next explicit Sign In Again may ask. A quit during the prompt is settled the same way at the next launch.
- **Sign Out** keeps the credential reference until the records are erased; launch retries an interrupted erase. If a Sign Out's erase was refused, a later Sign In for that identity asks to delete the old record and rolls back if refused again.
- The prompt window (`allowingInteraction:`) is one synchronous call on the vault actor. It flips the process-wide legacy Keychain switch, so it is exactly one deletion **per vault**; another vault actor (for example the offline store's) could still run a call inside that window.
