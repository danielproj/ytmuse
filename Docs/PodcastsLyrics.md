# Podcasts, episodes and source lyrics (W18)

Design notes for the podcast and lyrics surfaces. The parsers are built on four REAL anonymous public captures (`Fixtures/W18-real`, labelled `real-public-anonymous-capture`: a song's `next`, its lyrics page, an episode page and a podcast show) and tested against them first; `Fixtures/W18` holds only the edge cases the captures do not show (`synthetic-test-only`, assembled by `Fixtures/W18/generate.py` from the real renderers). Everything below that depends on what the SIGNED service answers is on the end-of-project live list at the bottom. Suite `T18` (`scripts/test.sh --suite T18`); the console was locked, so the native UI part is written and **pending**.

## Reading the service

- **Episode rows** (`musicMultiRowListItemRenderer` on a show page) now carry `MusicCatalogItem.episode` (`MusicEpisodeInfo`): the service's `playbackProgressPercentage`, the length it printed, whether a "Played" label exists, whether a position-feedback token exists, whether the row's menu carries YouTube Music's own `offlineVideoEndpoint`, and the row's description. Accounting is unchanged (`items == classified + skipped + unsupported + duplicates` against an independent walk of the raw JSON).
- **Episode page** (`browse MPED…`, `MusicEpisodeParser`): title, byline ("5 views • Sep 23"), the show (strapline link, else the "Go to podcast" menu item), thumbnails, progress, description, and the Episodes-for-Later toggle. Every header section, button and menu item is counted as recognised or ignored BY NAME (`MusicEpisodeAccounting`); a page with no title or no play target is `.unrecognised`, never an empty episode.
- **Lyrics** (`MusicLyricsParser`): `next` for the song (`videoId`, `isAudioOnly`) → its tabs are classified by endpoint `pageType`/content, never by title → the Lyrics tab's browse id → `browse` of that id. The real lyrics page is **plain text in `musicDescriptionShelfRenderer` with a source footer ("Source: Musixmatch") and no timing**. The text and the footer are returned byte for byte (no trim, no normalisation; asserted against an independent extraction and on a fixture with whitespace edges).
- **A `next` response with no up-next tab is not a watch-next page** and is `.unrecognised`; "no lyrics" is read only from a well-formed `next` that offers no selectable lyrics tab (or a lyrics page that holds a message/empty text). An unreadable answer is an error ("couldn't load"), never "no lyrics".
- **Transport.** `/youtubei/v1/next` is a fourth *read* path (public and signed allowlists; the exact-set assertions in the older suites were updated to the new set, not relaxed). Lyrics are read signed when an account is active, in case a signed answer supplies timing, and anonymous otherwise, through `MusicSessionCoordinator.lyrics` with the usual account-scope fence.

## Findings in the real captures (recorded, not assumed)

1. **Every real episode row prints a "Played" label next to a progress of 0.** The label is furniture, not state: reading its presence as "played" marks all 20 rows of the real show played. Only the percentage reaching 100 means played; a test asserts none of the 20 real rows is. (The scale of `playbackProgressPercentage` is taken from its name — 0…100; anything outside is unreadable, not clamped.)
2. **Every real episode menu carries `menuServiceItemDownloadRenderer` → `offlineVideoEndpoint`.** It is the web client's action on YouTube Music's own offline store, not a permission to keep the media on this Mac; the addendum forbids the extraction a file would need. It is parsed only to be counted and recorded (`publishesServiceDownloadAction`) and **never becomes a control**: `DownloadEligibility` still answers `notOffered(.youTubeMusicNoMacDownloads)` for every real episode id (tested), and the episode page and show page state why in words (`DownloadCapabilityNote`). No source in the repository publishes an explicit per-item download permission, and none was invented.
3. **The service's own "remove from Episodes for Later" also carries `ACTION_REMOVE_WATCHED_VIDEOS`** (it clears every watched episode from the list). The write this app sends names the one episode only (`ACTION_REMOVE_VIDEO_BY_VIDEO_ID`); a test asserts the extra action is never sent although the real page publishes it.
4. **Anonymously the Episodes-for-Later toggle publishes only its remove side**; the add side is a sign-in modal. A direction is offered only when the page published it (`addPublished` / `removePublished`), and only to a signed-in listener.
5. A row prints a day and month without a year ("Sep 24"), so **no date order is offered** (see Sorting).
6. The real lyrics page has no timing. Timed lines exist in the model for a source that prints them (the reference clients' `timedLyricsModel` shape, exercised on a `synthetic-test-only` fixture with invented placeholder text); a malformed timed answer (out of order, no cue range, end before start) is refused whole, never repaired.

## Behaviour

- **Show page.** Episode rows show their progress with whose figure it is — "From YouTube Music" for the service's percentage, "On this Mac" for this Mac's record — and a Play button that starts the show's playlist at that episode (the playlist the page published, else the show's `MPSP…` id minus the prefix). Sorting (service order, unplayed first, shortest, longest, title A–Z/Z–A) is a stable view over the service's order; nothing is dropped. The header carries the show's listening speed and the skip lengths.
- **Episode page** (`EpisodeDetailView`): header, progress line, Play/Resume (disabled with the reason when signed out), Mark as Played/Unplayed (this Mac only, reversible), Save for Later / Remove from Episodes for Later (signed in, one request per press, through the Library's ledger), chapters, the description (native rich text), and the download explanation.
- **Speed and jumps.** 0.5×–3× (`PodcastRate`; a value outside the bounds is refused, never clamped), remembered per show and with a default for shows without their own; 15 s back / 30 s forward by default, each customisable from fixed lists; jumps clamp to the item. The hidden player gets one new command, `rate`: the page's own `<video>` keeps `preservesPitch`, the element's rate is read back, a page that ignored the request answers `rejected`, and an ad answers `ad` (nothing is changed during an ad). The speed follows the item: an episode plays at its show's speed and anything else — a song after an episode — returns to 1×. Episodes that follow inside the show's own playlist are recognised as that show's episodes.
- **The speed is what the element reports (rework 1).** The page's periodic media report now READS `video.playbackRate` (and a `ratechange` posts it at once); the app reconciles `confirmedRate` from it on every report, so a new item, a full load, or an ad that changed the element's speed is seen, not assumed. The transport and Now Playing show the actual speed (and say what was chosen when they differ), and the chosen speed is re-applied only to the episode. An advertisement is always 1×: if the element reports another speed while an ad shows, the player returns it to 1× (`normalSpeed`, which only ever sets 1 and re-checks inside the page that an ad is still showing, so a restore that lands after the ad ended does nothing). A page that refuses is asked once per ad and the element's real speed stays shown. No speed command is sent during an ad. The old script guard now bans SETTING the speed anywhere but the `rate`/`normalSpeed` commands, not reading it.
- **A show's own Play/Shuffle** registers the show's playlist with the podcast controls exactly as an episode's Play does (speed, progress, resume). Registration happens only AFTER the start has happened (never for a start that failed, went stale, changed account or was refused as busy, so what is already playing keeps its registration), and only for Play and Shuffle — a show's radio or any other page action never registers its items as episodes.
- **Progress and resume.** This Mac's record (`EpisodeProgressRecord`, one private 0600 file per account in the app's data directory, removed with the account) is written for episodes the person started from a podcast surface, every 5 s of position, on pause, and at the end (within a second of the end = played). Resume seeks once, to the exact position this Mac recorded; a service percentage is a figure, never a position. Nothing is sent to the service: YouTube's own player reports its progress by itself when the hidden player plays; the app neither writes nor imitates it. The position-feedback token is parsed and counted, never sent (a source sweep asserts the podcast sources contain no write path).
- **Chapters** come only from the timestamps the description itself prints, by the rules the service's own player applies (starts at 0:00, at least three, at least ten seconds apart, ascending, none past a known length). A description that breaks any rule has none; the real episode has none.
- **Lyrics panel** (`LyricsPanelView`): plain text selectable, the source footer verbatim, and the honest note "These lyrics came without timing…". For timed lyrics: exactly one line is current (the last whose start has passed), tapping a line seeks only when the player will take a seek (not during an ad), a person's own scrolling stops the following until "Return to Current Line", and Reduce Motion makes the scroll a jump. "No lyrics available" (a result) and "couldn't load" (an error, with Try Again) are different states.

## What the tests cover (T18)

- **T18.1** — rate bounds (0.5–3), per-show restoration across a relaunch, skip defaults (15/30) and customisation, jumps clamped, speed follows the item, resume once, chapters from actual timestamps
- **T18.2** — local progress is "On this Mac" and never presented as the service's, a "Played" label is not played, the service's percentage is not a position, the progress file is private and per account, the one write (Episodes for Later) is one request per press through the ledger and names one episode, episode download eligibility is unchanged
- **T18.3** — missing lyrics stay missing, untimed lyrics stay plain and verbatim with their footer, no timing is inferred, "no lyrics" ≠ "couldn't load", no external provider is named or reached (source sweep), timed shapes that are not well-formed are refused
- **T18.4** — one current line, never backwards, equality at the boundary; manual scroll is stable; Return to Current Line; line seek only when supported; Reduce Motion avoids the scroll animation; rendered at the side panel's widths

Real-capture coverage: all 4 captures parse with every renderer accounted for against independent walks of the raw JSON (episode page: 2 sections, 3 header buttons, 6 menu items; show: 20 of 20 episode rows; next: 4 of 4 tabs; lyrics: the one description shelf, text byte-identical).

## Not verified live — the end-of-project list

- **Signed shapes.** Whether a signed `next`/lyrics `browse` supplies timed lyrics, and in what shape (the reference clients' `timedLyricsModel`/`cueRange` form is assumed and fixture-tested only; a signed capture of a song with timed lyrics is needed). Whether the signed lyrics page differs from the anonymous one in any other way.
- **Episode progress.** The scale of `playbackProgressPercentage` in a signed capture of a part-played and a fully played episode (assumed 0–100), whether `Played` text/colour or another field marks a finished episode, and how the signed episode page reports it.
- **Episodes for Later.** The signed add-side endpoint (assumed `playlistEditEndpoint` `ACTION_ADD_VIDEO` on `SE`), the answer `browse/edit_playlist` gives (assumed `STATUS_SUCCEEDED`), and that a single-episode remove without `ACTION_REMOVE_WATCHED_VIDEOS` is accepted. Reading `VLSE` back to settle an unknown outcome uses the episode page's own state.
- **The hidden player.** The `rate` script still falls back to writing `video.playbackRate` itself when the page's `setPlaybackRate` did not apply it: whether the page's API alone suffices is on this list (the element's speed is now observed either way). That `playbackRate` changes the real audio speed with pitch preserved (the script requests it and reads the element back; the audible result is unobserved), that the rate persists or resets as assumed across the show's next episode, that `list=PL…&v=<episode>` starts that episode (the Catalog list already carries the show's `PL…` playlist), that a seek works at the resume position as soon as the item reports a length, and the real feel of 15/30 s jumps. Power: the progress beat is a native 5 s timer that only reads while an episode plays.
- **Lyrics panel on a playing song.** Highlight latency (the hidden clock publishes once per displayed second), manual scroll feel, Return to Current Line, line seeks and Reduce Motion with real playback; VoiceOver on the new screens.
