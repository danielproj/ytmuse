# Uploads (W19)

Design notes for the Uploads screen and the upload job workflow. **No live upload exists in this version**: the real YouTube Music locker upload route is W37. Everything here that touches the service's upload side runs against a scripted transport in tests and in the labelled development mode, over synthetic audio the app writes itself. A generic YouTube video upload is never a substitute.

## What the person sees

- **Uploads** is a destination of its own (sidebar: History / Uploads / Podcasts). It shows *Songs*, *Albums* and *Artists* the person has already uploaded, read through the Library's own collection model and parser (`LibraryCollectionModel` over `MusicBrowseParser.Mode.collection`; the page ids are `MusicUploadKind`).
- **Capability, as it really is.** In the application the transport is `UnavailableUploadTransport`, so the screen says "Uploading arrives in a later update" and offers **no** upload control and no drop area (not an inert or fake one). Choosing or dropping files is offered only when an upload route reports itself available. The screen then also states what the route says about itself (resuming, a size limit *only if the route published one*) and nothing else.
- **No invented limits.** The app never says which formats or sizes YouTube Music accepts. Local checks are about the file: it is a regular, readable, non-empty audio file (first bytes name an audio container, or at least the extension says audio), not a video container, not copy-protected (`M4P`), and it holds still while it is read. The service decides the rest after the upload and its own words are shown verbatim ("YouTube Music said: …"). A size limit is enforced only when the transport publishes one. The app's own batch limit (100 files per choice) is named as the app's.

## Jobs (`UploadQueue`)

States: queued → uploading → processing → completed, plus failed, cancelled and interrupted. `UploadJob.allowed(from:)` is the whole transition table: *completed* is reachable only from *processing*, a completed or cancelled job never moves again, a failed one only by a new explicit attempt.

- One transfer at a time; the same file (path, size, modification time) already in the list is refused as a duplicate, once per choice and across choices (a cancelled or failed one doesn't block choosing it again).
- **Success needs the service's word.** After the bytes are sent the job is *processing*; the service's processing status is polled (bounded cadence, errors counted). Only `completed` from the service moves the job to *completed*, and only then the Uploads lists are read again (`UploadsSurface.refreshLists`). A processing failure or a refusal when sending never refreshes anything and never shows a library item. A job still processing after the last scheduled check is not a failure: it says so and can be checked again by the person.
- **Resumption only where the route supports it.** `UploadCapability.resumption`: with `.supported` an interrupted job offers **Resume** and the route gets its own handle back; with `.unsupported` the job says "YouTube Music can't resume an interrupted upload, so it has to start over" and offers **Start Over**, which is the person's explicit action (never automatic, never a second job: one job, `attempts` + 1). Nothing is queued offline.
- **Restart.** Job records are kept per account (`UploadJobFileStore`, a private 0600 plist per account in the app's data directory; removed with the account). After a restart a job that was queued or transferring is *interrupted* (nothing restarts by itself); one the service already holds is watched again. A list that cannot be read is reported, never shown as empty.
- **Account scope.** `accountChanged()` stops every transfer, tells the transport to drop what it held, releases every file lease, keeps the old account's jobs under the old account's key and ignores anything the old transport reports afterwards. The new account sees only its own jobs.
- **Files.** Access is read-only and per job (`UploadFileLease`, security-scoped when the system gives a scope), released the moment the transfer ends, and refused if the file is no longer the file that was chosen (size/modification time). Nothing in the upload code writes, moves or deletes a chosen file; cancelling or dismissing a job removes only the app's own record.
- **Test mode** accepts only files under the app's own synthetic-samples folder (the owned-file check), through a link or not.

## Remote removal (`UploadRemovalModel`)

Removing an upload deletes it from the person's Music locker — a real account write. It happens only as `request` (names the upload and asks; sends nothing) → `begin`/`confirm` (the destructive button of a dialog naming the upload and saying the file on the Mac isn't touched) → one request. It is offered only for an upload whose own library page published a removal target (`musicDeletePrivatelyOwnedEntityCommand.entityId`, read from its menu; ambiguous or malformed → none; no id is derived or guessed). The model holds no file and has no path from picking, queueing or uploading a file. The request is `POST music/delete_privately_owned_entity {"entityId": …}`, the request ytmusicapi's `delete_upload_entity` sends (a pinned reference copy of its upload code, commit `4da34b68…`, is kept under `artifacts/harness/nodes/W19/reference` with its hashes, and `UploadReferenceComparisonTests` compares endpoint, body, target location and the three library pages against it on every run) (one more allowlisted write path; the same writer closure the Library ledger holds, still the app's one `write` call site). Success needs positive evidence (`actions`); an `error` is a refusal; anything else is *not confirmed* and the Uploads list is read before anything is sent again (the upload being gone is the evidence).
