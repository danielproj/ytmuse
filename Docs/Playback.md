# Native playback (W06)

`PlaybackSession` is the queue-aware product transport owner. All current app windows share the same `PlaybackModel` and `AppPlaybackAuthority`; views never construct a player. The authority closes its old session before opening a replacement, rejects pending initialization after an account barrier, and is registered with `AccountLifecycle`. Every replacement constructs a new queue owner, boundary and Domain command owner. Explicit application Quit uses a termination delegate that awaits stop/checkpoint before allowing termination. Workspace sleep/wake observers are registered once on the authority, independently of window count.

`NativePlayer` actor confines one AVPlayer. A URL comes only from `NativeAssetProvider`, after the separate `PlaybackResolver` and capability checks. Context admission rejects obsolete account/item generations before hardware operations; preparation and seek completions have additional revisions. Preparation acknowledges ready-to-play, play acknowledges the native time-control state, and position/end/buffering/failure callbacks retain their captured context and shared monotonic timestamp. Observers are removed on replacement/stop. There is no secondary recovery player or web fallback for owned media; YouTube Music playback uses the separately approved hidden player described below.

The current app exposes a deliberately selected **Owned test audio · Not YouTube Music** mode. It uses the two bundled CC0 generated sine signals and a separate local database namespace, with no credentials or service identity in the real account roster. Normal launch does not initialize this player or autoplay media. The button starts the test queue at 0.08 independent app gain; automated render evidence uses 0.001. No system volume/device changes, microphone capture, other-app audio capture or remote source calls are used. Source metadata is inspected from the actual local file. The panel reports Unknown for unavailable measurements and system-default output without claiming a measured device format or bit-perfect output.

## Transport and policies

Product Play/Resume goes through the committed queue resume path, resolving the same occurrence at its checkpoint with a new playback token. This also settles W05 L1: pause, late end, then Resume reconstructs a playable native item; it never calls Domain play on an ended player. Previous restarts when elapsed position is greater than three seconds, otherwise selects the prior occurrence; the direct previous-item interface bypasses that threshold. Queue history/advertisement/immutable protections still apply. Next, selection, shuffle, repeat and edits go through QueueCommands. Same-generation position/started observations preserve unrelated edit undo (L2); a Domain user pause after exhaustion blocks late recommendations (L3).

SwiftUI retains the scrub preview locally and commits on gesture end. `coalescedSeek` replaces pending keyboard targets with a 120 ms idle window. Seeking during resolution keeps the latest target in Domain and applies it after readiness. Native seeks cancel older pending seeks and use zero tolerance; stale completions cannot acknowledge a newer gesture.

Best available is the default quality preference; Data saver selects the lowest known bitrate, Best available/Auto the highest known bitrate among the resolver's supplied variants. Buffering never silently changes that preference. The owned provider supplies one PCM variant. The interface is ready for W34's authorized, compatibility-filtered source variants and actual Auto adaptation; this is no evidence of live Music quality selection. AVPlayer decodes directly, with no application transcode, EQ, normalization or crossfade. Rate (0.5–3), app gain and independent mute reach AVPlayer. Balance and next-item prebuffer scheduling explicitly return unsupported until W16 supplies the appropriate measured backend; there are no functional-looking DSP controls.

A typed authorization failure triggers one refreshed preparation/resolution, then a typed terminal error. Metadata expiry can trigger one renewal and position restoration before the deadline. A terminal `failed(expiredMedia)` retains the accepted Domain contract and is not reinterpreted as renewed permission. Eligibility/revocation failures remain distinct. Refresh while paused preserves pause intent. Temporary offline failure becomes buffering; `recoverNetwork` revalidates/resolves at the checkpoint only while play intent remains active. A later pause, route loss, account switch or quit prevents recovery. Actual route/path detection and source-specific error classification remain integrations for W22/W34.

An explicitly selected failed item remains selected with Retry. Unattended sequential resolution failures remain identifiable in the queue and append bounded local failure records; processing stops on the third consecutive failure. These local failure records are stored atomically with the queue, respect pause/clear local history, and contain category/occurrence/media/time, never media authorization. They are not fabricated listening events or remote history writes.

Sleep timers support 5/15/30/60 minutes, custom positive duration, and End of item. A wall deadline counts sleep time; monotonic time controls the five-second gain fade. Fade completion pauses without consuming/changing the current occurrence, restores the user's gain, and clears the timer. End-of-item starts fading in the last five wall seconds (accounting for playback rate), and an end arriving during the timer pauses without queue advancement. Cancel restores gain; account detach and explicit Quit cancel all timer/scrub/event tasks. Expired timers, including a fade interrupted by sleep, prevent wake resume. The session accepts safe-route/resume preference inputs; the current app's workspace wake adapter uses safeRoute=false until actual route reconciliation is integrated, so it cannot leak audio to an unverified route.

### Sleep timer for YouTube Music playback (P17-WEB, PLAY17)

One sleep timer for the application session, two engines. The native session keeps its own (above); the hidden YouTube Music player has its own, in `Playback/WebMusic/WebMusicSleepTimer.swift` (logic) with `WebMusicCommand.fadeVolume` / `WebMusicScripts.fadeVolume` (the one new page command). `PlaybackModel.sleepTimerDisplay` is the single read the surfaces use (the bar, Now Playing, the popover, the mini-player), `PlaybackModel.setMusicSleepTimer` the single call that sets the hidden player's timer (the menu and the App Intent both make it, through the output gate), and `sleepTimerToCarry` moves a running timer across a change of engine (what is left of it, or End of item; a fade already under way is not carried).

- **Presets and lengths.** 5, 15, 30 and 60 minutes, a custom length (more than 0 and at most 24 hours), End of track / End of episode (one `endOfItem`; the menu words it by the item that plays). A running timer is replaced by a new one. The deadline is a wall instant, so time asleep counts.
- **At expiry while it plays: fade, pause, level back.** The fade is 5 seconds in 0.25 s steps. Each step scales the page `<video>` element's OWN volume (`video.volume`, never the player's saved volume, so nothing is persisted) from the level it had when the fade began, which the page remembers (`window.__ytmuseFade`). The factors follow the monotonic clock (`1 - elapsed/5`), so a changed wall clock can neither stretch nor skip the fade. The last step is silence; then the EXISTING `pause()` command path runs (intent off, the revision moves), and a final `fadeVolume(1)` puts the level back so the next Play starts at the level the person had. Nothing else reaches the page: no seek, skip, queue or volume command (`WebMusicSleepTimerGuardTests` sweeps the file for it).
- **Advertisements are never faded** (Playback addendum: a fade of an ad is a mute in effect). Enforced twice. Natively: an ad in the snapshot at expiry means pause only and no fade command at all; an ad that appears during a fade first puts the level back (`fadeVolume(1)`, which only raises it) and then pauses. In the page, at the instant of each step: the script checks `ytmuseAdShowing()` BEFORE it lowers anything and answers `ad` (putting back a level the fade had lowered), and the native side then only pauses. The pause itself is allowed during an ad, as everywhere else in the app.
- **Who is in charge.** A person's pause, play, seek or Next during a fade ends a length timer and puts the level back; a new request (another playlist) or a replaced document does the same (a document that was never faded gets nothing sent). A person's own volume command takes over from the fade (the page forgets the remembered level; the next step starts from the person's). A page that cannot be faded (no media, volume refused, not answering) is paused without a fade; it is never reported as faded.
- **End of track / End of episode** pauses at the item boundary the PAGE reports: its duration and position, the position carried forward at the element's real speed between reports, and its `ended` event. The fade covers the last 5 media-seconds (scaled by the speed) and reaches silence 0.3 s before the end, where the pause is sent so it lands at the boundary and not in the first moment of the next item. If the page already moved to another item without our pause (a late report), it pauses at once. A page that reports no duration (a live stream, an item not yet known) has no boundary: the timer waits and invents none, and End of item is refused for a live stream. Seeking back out of the last seconds ends the fade and keeps the timer for the new end. An ad before the boundary is waited out.
- **The page must not resume by itself.** After the timer's pause, a page that reports playing again is paused again, at most three times, until a person's command (the guard compares the command revision recorded at the timer's pause).
- **Cancel and expiry rules.** Teardown of the player (account switch, sign-out, removal, explicit quit) cancels the timer and sends the dropped page nothing. A timer that ran out while the Mac slept keeps the wake from resuming (`PlaybackModel.holdFacts` asks `sleepTimerHasExpired()`, and `resumeAfterSystemWake` checks it itself); the expiry is remembered after the timer is gone, until a person's command. Expiry with nobody wanting sound (a pause, a route loss, the hold for sleep) fades and sends nothing.
- **Remote routes.** The hidden player follows the Mac's output and always fades (`RouteCapabilities`); enabling its timer goes through the same gate (`.enableTimer`, engine `.youTubeMusic`) and so never shows the receiver note, which belongs to the native engine on AirPlay external playback.
- **Now Playing** is told by the player's own change (the timer's `pause()` publishes paused with no window open, W23 R3-1); the fade itself is still "playing".
- **Validation.** `WebMusicSleepTimerTests`, `WebMusicSleepTimerScriptTests` (the shipped script in JavaScriptCore), `WebMusicSleepTimerGuardTests`, `LifecycleWebSleepTimerTests`, `NowPlayingSleepTimerTests` and `IntentWindowAndTimerTests`, all against a fake page and manual clocks. Real fade audibility, a real expiry, the page's real `<video>` volume and real ad detection are on the end-of-project live list (never counted as passes).

## W06 R1 transport corrections (supersedes the original worker claims)

Pause now samples only prepared Domain media under the queue transaction gate, before rotating its token. A resolver with no prepared media cannot overwrite a deliberately committed queue checkpoint (the unchanged W05 F3 regression). The pause boundary retains a checkpoint-only mapping from the old exact engine context to the newly committed pause token until Domain's hardware-pause checkpoint is durable. This records the final frozen position even when the first database save is slow. That mapping cannot authorize EOS, is cleared on selection/detach, and still uses `checkpointFor` token fences. Each queue transaction saves before publishing. Superseded pause dispatches cannot pause a newer Domain generation; an early reserved selection can still be cancelled. Quit invalidates the generation immediately, then performs stop/checkpoint successfully rather than failing an old-context pause.

Desired app gain/mute are account-scoped engine controls, independent of whether an item is prepared. They are applied and observed before every prepare/play, retained across item replacement and cold-restored sessions, and rejected for an obsolete account owner. Timer gain is now a separate multiplicative envelope; it never replaces the desired app gain and is reset on item stop/replacement. All windows bind their sliders to one observable desired gain. New control requests supersede old acknowledgements without exposing expected stale acknowledgements as user errors; genuine rejected settings roll back the desired value. Snapshots distinguish desired and applied gain.

Unattended failure counting includes resolution/prepare failures and mid-play failures. Starting another item does not reset the chain. A successful natural completion resets it; an explicit new user sequence (selection/context start, Resume/Retry, Next or Previous) starts a new chain. A third consecutive failure pauses on that failed occurrence, with exactly one bounded local history entry per failed occurrence. Pending automatic advancement carries a sequence revision and cannot reclassify a newer explicit user selection as unattended. Required ads/immutable entries remain protected. Explicit Next uses a queue transaction that wraps Repeat All with the same eligible repeat population; Repeat One affects natural completion but does not repeat the item on explicit Next.

After natural queue exhaustion, seeking is unavailable: the normal timeline is disabled and a late seek call leaves the ended state, intent and queue unchanged. It cannot invent an occurrence, start audio or expose staleContext/Retry. A deliberate Resume remains a separate transport operation.

The owned start button captures a scoped, non-forgeable request permit synchronously before scheduling its Task. Account detach and Quit invalidate permits, including requests queued before the barrier and requests held during initialization. Tests hold these orderings explicitly instead of relying on millisecond delays. A fresh post-barrier click can open a new paused owner.

## YouTube Music through the hidden player (E01 lane P1)

`Docs/Playback-Addendum.md` (the account holder's decision of 2026-10-28) permits one hidden `WKWebView` running `music.youtube.com`'s own player as the YouTube Music audio source. Everything the user sees and touches stays native. This supersedes the Native boundary row, PLAY02 and PLAY15 for YouTube Music only; AVFoundation remains the engine for owned media.

**Single owner.** `AppPlaybackAuthority` owns at most one of the owned test-audio `PlaybackSession` or the `WebMusicPlayer`; starting either tears down the other. `restorePaused` only records the active connected identity's generation: nothing is created, loaded or played at launch, after sign-in or on restore. The page is created on the first explicit Play. Account switch, sign-out, removal and Quit tear the player down (media paused, handlers/observers removed, view and window released, non-persistent store cleared). A permit captured at the Play click is invalidated by any account barrier.

**Session.** `MusicPlayerCookies` (AccountSession) reads the active generation's exact Keychain record and hands the allowlisted `.youtube.com` cookies to the player, marking the cookies the website itself sets HttpOnly as HttpOnly so page script cannot read more than on the real site. The player's `WKWebsiteDataStore.nonPersistent()` store receives them before the first document; Google's full web session lives only in memory. A `WKHTTPCookieStoreObserver` reports store changes; the player debounces them against the installed baseline and `recordRotation` merges allowlisted `youtube.com` values and writes them back through `SessionVault.replace`, fenced on `AccountLifecycle.accepts` and the vault's bound generation. Google-domain cookies are never added to the record.

**Navigation.** Main-frame navigation is limited to `https://music.youtube.com`; a redirect to Google sign-in/consent is refused and shown as "sign in again" (an observed blocker, never a reason to widen storage); new windows are refused; subframes/resources are YouTube's own (non-web schemes refused) so nothing about advertising is filtered. The first document loads `watch?list=<playlist>&ytmuse_doc=<n>&ytmuse_load=<m>&ytmuse_play=1`; later playlists use the in-page router (`resolveCommand({watchEndpoint:{playlistId}})`) with a full-load fallback bound to the same load generation (immediately on router refusal, or after 15 s without a confirming sample; a second timeout fails visibly). Later documents use `location.replace` so WebKit history does not grow.

**Bridge.** One `WKScriptMessageHandler` (`ytmusePlayer`). `WebMusicBridge.validate` accepts only the `https://music.youtube.com` main frame of the current web view, the document generation native code reserved last (committed via `didCommit`), and the current load generation; payloads are type/size/key-allowlisted (≤16 keys, ≤512 B text, ≤6 KB total; artwork only from YouTube image hosts). Swift sends only `WebMusicCommand`s: constant script bodies run with `callAsyncJavaScript` and typed, validated arguments (playlist ID regex, finite seek/volume ranges). Page strings are never evaluated; no cookies or tokenised URLs are logged.

**Scripts.** Document start (main frame): reads the native generations and play intent from the URL; pauses any media start without native intent; wraps `navigator.mediaSession` so the page registers no action handlers and its metadata goes to the observer instead of WebKit's Now Playing. Document end: reports playing/buffering, position, duration, video ID, title, artist, artwork and ad state from the `<video>` element and the player API, plus `ended` and player error codes. Ad detection (adapted from Kaset, see THIRD_PARTY_NOTICES.md) uses `getPresentingPlayerType(true) === 2` and the `ad-showing`/`ad-interrupting` classes. These are undocumented YouTube signals.

**Ads.** Never blocked, skipped, muted, hidden or sped up. During an ad the transport shows an "Ad" badge, the selected track's title/artist/artwork and content clock stay, Now Playing keeps the track with rate 0 and seek disabled, and seek/next/previous are refused natively and again inside the page. Pause remains available.

**Native ownership.** `NowPlayingCenter` (SystemIntegration) publishes title, artist, artwork (fetched credential-free from YouTube image hosts, bounded), duration, elapsed position and rate, and registers play/pause/toggle/next/previous/change-position remote commands, admitted synchronously against the same player state as the transport bar (a refused seek reports failure to the system). It is relinquished when the player is torn down. No keyboard tap.

**UI.** When a YouTube Music account is active, the window shows the library playlists (the existing `FEmusic_liked_playlists` read) with Play buttons and a glass transport (artwork, title, artist, previous/play-pause/next, seek with elapsed/remaining, buffering/error states, Ad badge, volume). The owned-audio panel stays reachable in a disclosure for tests; without an active Music account the original owned panel is unchanged. The page lives in its own never-ordered-in window, so closing the main window does not stop audio; Quit stops it. If live testing shows WebKit will not start media there, `defaults write local.native-music.development YTMusePlayerHostOrderedIn -bool YES` orders the host window in fully transparent, 1×1 and click-through.

**Validation.** `PlaybackTests/WebMusicTests.swift` (bridge origin/subframe/stale/malformed/oversize, constant command construction, transport/load fencing, ad state, router fallback, no autoplay, teardown and authority barriers, Now Playing/remote mapping), `AccountSessionTests/MusicPlayerCookiesTests.swift` (Keychain bootstrap, rotation write-back, stale generation) and the fresh-process `WebMusicPlayerProbe` (cold WebKit, non-persistent store, configuration, cookie observation, teardown). None uses the network, a real session or audio. A working hidden player proves playback through YouTube's own web client for this account only; it closes no G01–G09 gate.

### Rework 1 (critic E01-hidden-player-opus-01)

- **Confirmation.** On the router path the outgoing track keeps reporting under the new load, so a load is confirmed only by evidence: the player's own `getPlaylistId()` equal to the requested playlist, or, when the page reports none, a different video. Unconfirmed samples publish no metadata. A fresh document needs no such evidence.
- **Ads and the timeout.** Ad samples (a pre-roll) suspend the load timeout without confirming. A load is never reloaded or failed while an ad shows, and the timer re-arms once content appears. Kaset's ad-pod continuity is ported to the page scripts and to the native transport: after an ad creative's video ID is seen, ad state holds until the content video returns, and an ad creative's `ended` is not a track ending.
- **Failures.**
  - A per-track YouTube player error is a notice; the transport keeps following YouTube's queue.
  - Every terminal failure (timeout, load failure, refused navigation, sign-in required, process loss, unreserved document, unreadable session) drops the page, so no failure is ever shown over audible playback.
- **Unreserved documents.** The bootstrap strips the `ytmuse_*` markers with `history.replaceState`. A page reload has no generation and no play intent. The host tracks the generation from the navigation's request URL at policy time, keeping it across redirects of that navigation, and a commit without one stops visibly ("YouTube Music reloaded by itself").
- **Signed out.** The observer reports `ytcfg LOGGED_IN`; `false` fails as "sign in again" instead of guest playback. Stored cookies are not widened.
- **Cookie write-back.** Rotation sends only the names whose value or expiry changed in the player's own store since its baseline, so a newer value the signed coordinator wrote is never rolled back.
- **Volume.** A level the user set is reapplied to a fresh page after its first confirmed sample; untouched volume is never sent.
- **Long text.** Long CJK and emoji titles are truncated on a character boundary (512 bytes) instead of rejecting the sample.
- **Background work (WIN10).** Now Playing is rewritten only on metadata, artwork, play or ad state changes or position jumps. The teardown notification replaces the 500 ms polling loop. Artwork is downsampled with ImageIO to 512 px after a 4096 px header check.
- **Keychain prompts (K1b).** `KeychainInteraction` disables the file keychain's legacy ACL prompt process-wide; `kSecUseAuthenticationUIFail` does not govern that prompt. Every vault query also carries `kSecUseAuthenticationUIFail`. At launch a record readable only after a prompt makes the identity "Session expired — sign in again", with local data kept, and Sign In Again writes a new record. See `Docs/Build.md` for stable local signing (K1a).

- **SS1, sign-in store in use.**
  - The sign-in sheet's SwiftUI host now holds the web view weakly and detaches it when dismantled.

### Follow-up 3 (first live audio, 2026-10-29): callback isolation

Audio started live: the app page loaded, there was no suspension, and WebKit reported `isPlaying`. About 3 s later the app trapped (NP1).

**Cause.** `MPMediaItemArtwork`'s request handler was a closure formed inside the `@MainActor` `NowPlayingCenter.update`, so Swift inferred it as `@MainActor`. MediaPlayer calls it on its private access queue, and the isolation check traps.

**Fix.** `NowPlayingArtwork.make` builds the artwork in a nonisolated context, with a `@Sendable` handler that only returns an immutable image.

**Audit of every framework callback in the lane:**
- **MPRemoteCommand targets.** They no longer assert the main actor. On the main thread the session's synchronous admission answers; elsewhere a thread-safe admission snapshot answers. That snapshot refuses seek, next and previous during an ad. Admitted commands are delivered on the main actor.
- **WKScriptMessageHandler relay.** `WebMusicMainActor.run`: synchronous on main, otherwise a hop.
- **Cookie-store reads and the `location.replace` completion.** Now awaited calls inside main-actor Tasks.
- **Sign-in KVO and cookie completion (M2 code).** The KVO closures are `@Sendable` (nonisolated) and hop through `WebMusicSignIn.onMain`; the cookie completion is awaited.
- **Unchanged:** WKNavigationDelegate (a MainActor protocol), the cookie observer and the NSWorkspace observers (they already hop), and the quit run-loop blocks (main by construction).

`CallbackIsolationTests` invokes the artwork handler, the real published artwork and the remote-command entry from background queues. Re-planting the old artwork construction traps the test process with SIGTRAP, as live.

Every YTMuse `XCUIApplication` in `Tests/NativeMusicUITests` sets `YTMUSE_UI_TEST_ISOLATED=1`, which (Debug builds only, see `IsolatedQAStorage`) puts the account database, window history, artwork cache, sign-in ledger and owned-audio store under a fresh temporary directory and both vaults in isolated keychain files. Google's grant store is not composed in that mode. Preferences are isolated as well (`AppPreferences`): every app and package preference read or write (appearance `@AppStorage`, sign-in options, the player host knob) goes to a throwaway plist in the temporary folder, never the `local.native-music.development` domain; isolated windows are non-restorable and autosave no frame, split-view or toolbar state, so `@SceneStorage` and window restoration cannot write the saved application state. A UI test that must survive a relaunch names a throwaway plist with a UUID token (`YTMUSE_UI_TEST_DEFAULTS_ID`); the app places it in its own temporary folder and the UI command sequence removes it. Under isolation, frame/split-view autosave and window restorability are also disabled at the class level before any window exists. The Release binary contains no such switch.

**Debug builds are isolated by default (C1 item 11).** The first decision at launch (`IsolatedQAStorage.decide`, taken once per process by `LaunchStorageDecision.establish()` before any store can open) is: explicit isolation (`YTMUSE_UI_TEST_ISOLATED`, design mode) always wins; the real stores need an explicit opt-in (`YTMUSE_USE_REAL_STORES=1`, or the launch argument `-YTMuseUseRealStores`); anything else, including a launch whose environment a sandboxed runner dropped, is isolated scratch storage (account database, owned-audio, preferences, window history, both Keychain vaults). An isolated instance also never creates or removes a WebKit identified store (its sign-in web view is in-memory and its store registry is a no-op). Release is unchanged and always uses the real stores. A Keychain read that fails only because interaction is disallowed is written to the roster as `expired` only by a Release build signed with a real identity (`KeychainExpiryPolicy`); any other build shows Sign In Again for that run only and leaves the stored state alone.

**Pictures and surfaces.**
- *YouTube Music.* The hidden page's own `<video>` picture is shown in a native view, scaled to fit with its aspect ratio preserved (`object-fit: contain`), with every control native. The SAME `WKWebView` moves from the hidden host window into the surface's view (`WebMusicPage.attachVideo(to:)`): no reload, no pause, no seek. The page is reduced to the picture by a constant script (`presentVideo`) that marks the video's ancestors, scales them to the viewport with a stylesheet and makes their siblings `visibility: hidden`; turning it off removes the marks and the stylesheet, which restores the document exactly (the probe compares a markup hash). Advertising is never covered (rework 1): the stylesheet gives NO ancestor a z-index or any stacking above the player's own layers. The player root and everything above it fill the viewport (`position: fixed`); what lies between the root and the video only fills its parent (`position: relative`); so the page's ad layers (`ytp-ad…`, `video-ads`), which sit after the video container inside the player root, paint above the picture exactly as the page lays them out, and they are exempt from `visibility: hidden`. The probe checks it with a hit test at the centre of every ad layer (it fails if anything paints above one), also with an ad playing; the ad creative's picture is shown like any other, before the load is confirmed too.
- *Not interactive (rework 1).* The presented picture is non-interactive: `VideoPictureView`/`NativeVideoLayerView` answer no hit test and are never first responder, and the web view itself (`NonInteractiveWebView`) answers no hit test, never becomes first responder, ignores key/mouse/scroll events and offers no context menu, so YouTube's page controls, shortcuts and WebKit's media menu cannot bypass the native command layer. Measured with real AppKit in the probe (`inputFacts`) and in `VideoSurfaceInputTests`.
- *One owner.* `VideoSurfaceOwnership` (inline preview, video window, full screen, Picture in Picture) allows at most one holder; a request takes the picture from the current holder in the same step, and only the holder's release changes anything. Closing the window, leaving full screen or ending Picture in Picture gives the picture back (to the previous surface, else the hidden host) without touching playback. Account switch, sign-out, removal, quit, owned-audio start and every terminal failure tear the page down, which releases every surface first; `PlaybackModel` closes the windows.
- *Picture in Picture* for the page's video is WebKit's own presentation mode of the element, offered only where WebKit reports `webkitSupportsPresentationMode("picture-in-picture")`; otherwise the button is disabled with that reason and a request is refused with it. WebKit enters the mode asynchronously, so "not active" reports are ignored until one says `active`; only active → not active is the system ending it, and a start that never becomes active is released with a stated reason. For owned and local video it is AVKit's supported content-source pattern, `AVPictureInPictureController(contentSource: .init(playerLayer:))`, where `isPictureInPictureSupported()`: each native surface is a layer-backed view whose BACKING layer is the `AVPlayerLayer` (never a bare sublayer under SwiftUI); the source view stays mounted in its window for the whole of PiP ("Playing in Picture in Picture" is stated over it), a stop is restored in place, and PiP is stopped before its source surface goes away. Real system PiP is never started by an unattended test (it crashed the system `PIPAgent`): `testW17NativePictureInPictureManualOnly` runs only with `W17_MANUAL_PIP=1`.
- *Owned and local video* is an `AVPlayerLayer` of the ONE `AVPlayer` the session owns (`NativeVideoHandle`), so a surface coming or going never adds a decoder or an audio output. The owned synthetic video (video-only, 480×270, 60 s) is generated at first use by `Playback/OwnedTestVideo.swift` in DEBUG builds only (nothing ships in Release), is reachable only from the Debug-only "Play owned test video" button, and is never YouTube Music evidence.

**Audio only (MEDIA03).** It asks YouTube for the audio (song) version where the service published one, and never covers a playing video: the picture is let go BEFORE the song is requested. Natively it disables the item's video tracks (`AVPlayerItemTrack.isEnabled`), which stops the decoder. Where the service published no audio version the video keeps playing and the notice says the picture is not hidden to fake audio only. The control is disabled with its specific reason when the page has not said song or video, when it is already the audio version, a live stream, or has no published audio version. Whether the web decoder stopped is stated only where it can be shown: when the audio version reports a picture the app says the decoder may not have stopped and could not be verified. A song with a published video version has a native "Show Video Version" control (switching is not one-way).

**Representation mapping (MEDIA02).** `RepresentationTransition.plan` carries the position only for a pair the SERVICE published (`PublishedCounterpart`, read from the queue item that matches the playing video, in the shape the service's `next` response publishes), with equal stated versions, and only if the two lengths then agree within 2 s (`settle`). Everything else — a same-title asset, another recording's song, a live stream — restarts and says why (`snapshot.restart`). Title, artist and duration alone never map two assets. The switch itself goes through the service's router (the playlist already playing plus the target's video id).

**Live (MEDIA05).** The page's `isLive`/infinite duration and `seekable` window give a relative window (0 = oldest reachable point). Seeks clamp into it; a stream with no window refuses seeking with the reason; Go live jumps to the edge only when behind it; "Live" is within 10 s of the edge; Previous never restarts a live stream. Downloads and crossfade are unavailable with specific reasons (`MediaCapabilityPolicy`): a live stream has no fixed length or end; YouTube Music items play in YouTube's own player, which the app can neither save nor overlap.

**Decoder measurement.** Native: an `AVPlayerItemVideoOutput` counts the pixel buffers the decoder delivers (28 in 1.2 s of video, 0 while audio only, 22 after returning to video). Web: `getVideoPlaybackQuality().totalVideoFrames` counts PRESENTED frames, so it needs a visible document; where the document is hidden the counter is 0 for the whole run and the probe prints `SKIP` for the decoder checks (never an ok) — the web decoder stop is UNMEASURED offline and stays on the live list. The unit tests prove the app reports web decoding true while frames advance and false once they go stale.

**Undocumented signals (live check required).** `isLive`, `musicVideoType`, the queue item's `counterpart`, `seekToLiveHead`, `getAvailableQualityLevels`/`setPlaybackQualityRange` and the captions module are YouTube Music page internals; every one is read behind a strict shape check, and an unrecognised layout reports nothing (so audio-only and switching stay unavailable rather than guessed).

**Validation.** `scripts/test.sh --suite T17` (see the W17 report for counts): `VideoTests` (mapping, live, capabilities, ownership, bridge, decoder meter, geometry, authority barriers, native AVKit decoder), the fresh-process `VideoSurfaceProbe` (the real hidden page against `Fixtures/W17`), the hidden-player regression classes, and one isolated native UI test.
