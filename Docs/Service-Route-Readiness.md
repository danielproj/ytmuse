## Exact evidence and implementation consequence

Official [Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app) documents Desktop registration, system browser, random-port loopback, PKCE and optional `client_secret` for token exchange/refresh. [OIDC](https://developers.google.com/identity/openid-connect/openid-connect) establishes validated Google identity. [channels.list](https://developers.google.com/youtube/v3/docs/channels/list) defines `mine`; neither API documents Music subscription or a Music-session exchange. Do not invent a one-use exchange endpoint beyond the actual OAuth authorization-code exchange.

## Native playback gate

The [video resource](https://developers.google.com/youtube/v3/docs/videos) describes embedded HTML rather than native variant delivery. [YouTube developer policies](https://developers.google.com/youtube/terms/developer-policies), III.E/H/I, separately constrain scraping, non-API access, audiovisual storage, ad interference, separation of audio/video and background players. A third-party library's software license does not grant service/content rights. A working URL, Premium account or ordinary user consent cannot by itself establish permission for this distribution route. A source-specific authorization decision is necessary; no legal conclusion about a hypothetical agreement is made here.

The missing resource is a YouTube/Google-authorized Music integration route covering this app/client and native delivery, with actual identity/channel binding, allowed reads, native asset/credential/origin/expiry and renewal rules, plus playback reporting and free/Premium ad eligibility. No such endpoint/SDK/contract was located in the inspected official materials. The evidence is scoped to those materials, not a claim that no private partner program exists. A policy approval/contact form is not itself a delivery API or a guaranteed approval path.

At this base, `OAuthTokenExchange.swift` validates and returns only `ValidatedGoogleProfile.subject`, dropping tokens at the stack boundary; `DesktopOAuthFlow` explicitly has no lifecycle installation path. `PublicMusic.swift` only performs public configuration/search/player metadata. `StreamResolver.swift` treats even `OK`/direct URL fields as `sourceGrantAndEventsMissing`. Historical [E01 observations](../artifacts/harness/nodes/E01/public-observation.json) were anonymous `UNPLAYABLE` without streamingData. They are not new receipts, current-account failures or native playback proof.

**Decisive next step:** parent resolves whether app-owned Desktop registration exists and whether a source-authorized Music integration resource is available. Authworker can finish the independent official profile/channel flow. After normal app consent, documented channel/read results can prove that narrower route. Only with permission to investigate the Music operation should a bounded account-menu/read attempt test Desktop bearer acceptance; it must preserve server denial and verify stable identity/channel separately. This worker does not authorize that private experiment. Even a successful read leaves the native-media gate closed until the source supplies the actual permitted delivery/events contract. Do not install Music Connected, weaken native admission or schedule extraction work to bridge the gap.
